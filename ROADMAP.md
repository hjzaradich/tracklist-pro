## 1. What we're building

A free, open-source (GPL-3.0) library manager for DJs who use **rekordbox 7** on Windows. It sits upstream of rekordbox and does four jobs DJs now do by hand:

1. **Build a Library out of the mess.** Start from your rekordbox collection or from nothing. The app finds music across folders and drives and groups duplicates, even re-encoded or re-tagged ones. It tells versions apart, picks the best file, gathers the best tags from every copy, and carries over what rekordbox already knows (BPM, key, cues, play counts).
2. **Keep it in step with rekordbox.** Send the Library via XML with correct tags and art. Read rekordbox's analysis and edits back. Flag fields edited on both sides for you to settle.
3. **Get tracks in.** Turn wishlists into owned files, and catch, identify and tag downloads as they land.
4. **Prep sets.** Crates and smart crates, your own tag vocabulary, harmonic "what's next", and playlists with an energy arc, all informed by what you've played.

**Audience: any DJ who uses rekordbox on Windows, whatever they play.** No genre or style is primary: bass, open format, house, techno, hip-hop, mobile and wedding DJs, and everything in between. Other DJ software and macOS aren't supported yet. The export layer is kept pluggable so they can come later (backlog). That means:
- **Versions are first-class:** edits, flips, bootlegs, VIPs, mashups, dubs, covers and pool edits (Clean/Dirty/Intro/Outro…), because many kinds of DJ use them.
- **Defaults are genre-neutral**, including the genre seed and the "what's next" tolerances.
- **Every setup is covered.** Anything that touches history or export handles laptop play (Performance mode), USB on CDJs/XDJs, and B2B sets.

### Guiding principles

- **The Library is the point.** The app builds order out of the mess; it is not a drive-tidying tool. Most DJs have years of work in rekordbox, so it's read from day one. Starting from nothing is fully supported.
- **Read-only outside the Library.** The app never moves, renames, retags or deletes files outside the Library folder. That includes Downloads and the files that linked Library tracks point to. Duplicate resolution is database-only.
- **Library tracks are durable.** A linked track depends on its file: it's flagged "file missing" if the file disappears, and the app warns when a track lives somewhere fragile, like Downloads. A managed copy (from Phase 2) survives its original disappearing, flagged "original file missing". Either kind is removed only by an explicit in-app delete.
- **Build what the current phase needs.** Tables, ports and services arrive in the phase that first uses them, not before.
- **rekordbox writes into files, so never assume a file is unchanged.** Identify files by their audio, re-read tags, and never treat a new modified time as new audio (§5.1).
- **A track is not a file, and versions are not duplicates.** Duplicates merge. Versions are separate tracks that are only linked, and nothing is inherited across a link. Identity is the fingerprint plus the version; paths only point to instances.
- **rekordbox performs, we prep.** XML is the guaranteed base. Reading the database and gig sticks are optional extras that fail gracefully. A field edited on both sides becomes a conflict you settle, never a silent overwrite.
- **No black boxes.** Every suggestion shows a short, plain-language reason alongside it at the moment it's made, e.g. "same key, +2 BPM, tagged Peak Time". That covers tags, genres, crate or playlist adds, best files, matches and next tracks. If the app can't say why, it doesn't suggest. ML output is labeled as the audio model's opinion and is never the only reason.
- **Everything in the app is reversible** through the operation log. The exception is what rekordbox does after you import a send, which the app can't undo. So the app merges conflicts first and guides the import (1.9).
- **Estimates are labeled** until rekordbox's analysis replaces them.
- **Offline by default, private always.** Every online service is opt-in and says what it sends. No telemetry.
- **Optional features are the user's choice.** The wishlist, metadata lookup, the audio model and any later integration are switched on by the user, one by one, and the app works fully with each of them off. A light feature ships inside the app and is only switched on; a heavy one (the audio model) is downloaded when the user asks for it.
- **Portable code, Windows release.** Paths are stored as volume identity plus a relative path. CI builds macOS and Linux, but only Windows is supported.

## 2. Library model

Three layers, fed by two read-only inputs:

```
┌─────────────────────────────┐   ┌─────────────────────────────┐
│ MUSIC FOLDERS (read-only)   │   │ REKORDBOX COLLECTION        │
│ every file → file record    │   │ (read-only) BPM, key, grid, │
│                             │   │ cues, plays, rating, color, │
│                             │   │ comments, My Tag, playlists │
└──────────────┬──────────────┘   └──────────────┬──────────────┘
               │ fingerprint +                   │ matched by location,
               │ version grouping                │ then relink (1.2)
               ▼                                 ▼
┌───────────────────────────────────────────────────────────────┐
│  TRACKS (`recording`)   one track ← N duplicate files         │
│  canonical tags + rekordbox data, genre, energy, history      │
└───────────────┬───────────────────────────────────────────────┘
                │ add to Library (linked, or rules gate + convert)
                ▼
┌───────────────────────────────────────────────────────────────┐
│  LIBRARY (linked tracks 1.8; managed copies 2.6)              │
│  durable; removed only in-app                                 │
│  → rekordbox XML send  ⇄ conflicts ⇄  rekordbox read-back     │
└───────────────────────────────────────────────────────────────┘
          ▲
   INBOX (watched folders): files stay put and get indexed
```

In the UI, **All music** shows the tracks layer and **Library** shows Library tracks. **Add to Library** moves a track from one to the other.

| `file_stage` | file_id, stage (read / hash / fingerprint), version, size, mtime, status (done / failed / skipped), reason, done_at | What each scan stage last did to a file, and at which size, mtime and stage version, so a stage redoes only changed files (1aB, 2026-09-29). **Failed** means the content couldn't be processed and waits until the file changes; a file that couldn't be reached is never failed, only skipped or left unrecorded, so it's retried. Deleted with its file. |
| `fingerprint_match` | file_a, file_b (the lower file id first), version, items_a, items_b, coverage_a, coverage_b, score, segments (JSON: offset_a, offset_b, items, score, alignment per matched stretch), compared_at | What comparing two files' full-track fingerprints found (1.4; 1bA-2, 2026-10-02): the share of each file the main alignment matched, the difference score over it, and every matched stretch with its offsets in fingerprint items. One row per compared pair, a pair where nothing matched included. The matching pass compares only the pairs its block index proposes; the grouping job adds the pairs it compares directly (same-named files and a mashup's named parts that the pass never proposed, and pairs inside a set of duplicates that nobody compared; 1bC-1, 2026-10-11), never every pair. Files with the very same fingerprint are linked to the first of them, which holds their results with other files. Derived state, measurements only: the grouping rules (1bB) read it and decide. The database deletes a file's rows when its `fingerprint` bytes change, and with the file row; a tag rewrite or a new modified time leaves them (§5.1). Not in the operation log. The definitions are in the `matching` module's docs. |
| `fingerprint_matched` | file_id, version, stands (the file whose results stand for this one: itself, or the first of the files with the very same fingerprint), matched_at | Which files' current fingerprints have been through matching, every result stored (1.4; 1bA-14, 2026-10-04). A present file with a fingerprint and no row is what makes matching due. Derived state: its row goes when the file's fingerprint changes or is cleared, when the file row or the row of the file standing for it goes, and when a missing file comes back (files that arrived meanwhile were never compared with it); it stays while a file is merely missing, as its results do. A row of another version than the comparison's counts as no row. |
| `file_quality` | file_id, audio_hash, method_version, cutoff_hz, cutoff_gap (too_short / silent / low_rate: why there's no cutoff), decoded_ms, header_ms, decode_errors, error_kinds (JSON counts by kind), ended (complete / cut_short / gave_up), failure, measured_at | The quality job's measurements for a file (1.6; 1bA-10, 1bA-11), one row per file, measurements only: the verdicts are worked out from them (1bB-6) and kept in `file_verdict`, never in `file.quality_verdict`. A row belongs to the **audio** it was measured from (`audio_hash`), not to the file's mtime (5.1): a file whose `audio_hash` still equals the row's is never measured again, and one with other audio is. `method_version` makes every row due again when the method changes. A file whose content can't be decoded gets a row with a `failure` and no measurements, and isn't tried again until its audio changes; a file that couldn't be reached gets nothing. Deleted with its file. |
| `file_verdict` | file_id, rules_version, inputs, verdict (ok / low_bitrate / suspect_transcode / truncated / broken, or NULL for none), findings (JSON array of {code, numbers}), assessed_at | The stored quality verdict of each file and the findings behind it (1.6; 1bC-5, migration 0021), worked out by `quality::verdict::assess` from the file's codec, bitrate and sample rate, the read stage's verdict and its `file_quality` row. **Derived state, in its own table:** `file.quality_verdict` is the read stage's own verdict (`truncated` / `broken`, cleared by every read) and an input to `assess`, so nothing writes the answer there. A row is current only while its `rules_version` is the build's (a version constant bumped with `assess`'s rules, so new thresholds re-assess every file from the stored measurements without decoding audio) and its `inputs` key equals the inputs now (any new measurement, re-read, audio hash or read-stage verdict makes it stale). It is settled by the quality job (at its start for every stale file, and for a file as its measurement lands) and by `quality::settle`, which whatever reads verdicts calls first; a stale verdict alone queues no job. A file with no row, a stale row or a verdict NULL has **no verdict**, read by `quality::stored_verdict` as none and never as `ok`. Deleted with its file. |
| `file_waveform` | file_id, audio_hash, method_version, duration_ms, peaks (a BLOB of byte pairs, one pair per bucket: the loudest sample, then the RMS level, each 0 to 255), failure, computed_at | A file's waveform for the player (1.11 "Audio"; 1cB-9, migration 0040), one row per file. **Derived state:** the `waveform` job decodes the file once and reduces it to at most 1024 buckets (at most 2 KiB; a shorter track gets one bucket per 256 frames), so 100,000 tracks take at most about 200 MB of the app database and nothing is ever written next to the music. A row belongs to the **audio** it was computed from (`audio_hash`), not to the file's mtime (5.1): a file whose `audio_hash` still equals the row's is never decoded again, and one with other audio is. A file that holds the very same audio as another (a duplicate, a copy in two folders, a file that moved) is given a copy of that file's row without being opened (an index on `audio_hash` and `method_version` finds it). `method_version` makes every row due again when the method changes. A file whose content can't be decoded gets a row with a `failure` and no peaks (the quality job's reasons), and isn't tried again until its audio changes; a file that couldn't be reached gets nothing. A row of other audio or another version reads as no row ("not ready"). Deleted with its file. |
| `recording` | canonical title / artist / version / remixers / label / year, genre_id, per-field provenance; display bpm / key / energy | A **track**. The display bpm/key/energy are **derived from `analysis`** and never edited directly. Its ids are never reused (`AUTOINCREMENT`, migration 0031): the grouping job (and a split) makes rows and the grouping job sweeps them outside the operation log, which stores track ids as values (see `operation` / `change`). |
| `analysis` | recording_id, source (rekordbox / tag / MIK / user / local / ml), bpm, key, energy, confidence | **The source of truth** for these values: several per track. Precedence: BPM and key go rekordbox > file tag > MIK > local; energy goes user > MIK > local > ML (the audio model is optional and never the only reason, so it ranks last). Disagreements are flagged. The track's shown values come from the `recording_display` view, so they can't drift or be edited directly. **rekordbox rows** (1aD-4): one per track, written by the attach job from the track's trusted rekordbox entries only (never a `relink_probable` row or one with no track). The entry matched to the track's best file gives the row, else the most played, else the lowest TrackID; the others stay in `rekordbox_track` for Review. A Library track another Library track was merged into (1.12, `track_merge`) takes it only from the entry it is sent as, the one on its linked file, never from an entry of the track that left; with none it has no rekordbox row (foreman's ruling, 2026-10-16). A row goes when its entry turns probable, unmatched or matched elsewhere. A merge drops the emptied track's rekordbox rows (attach recomputes them) and moves its other sources' rows to the surviving track, which keeps its own when both have one. **The user's energy** (1cB-8, migration 0039) is the track's row with source `user`, energy only: the keys 1 to 0 insert it or change it, for all the selected tracks in one operation (`set_energy`, `src/energy`), and Undo takes it back, so the next source's energy shows again. A track already at that energy is left alone. Its ids are never reused (`AUTOINCREMENT`), because the operation log records it while the scan, the attach job and the local estimate insert `analysis` rows outside the log; a row that gives no BPM and no key doesn't put the track back in the search index's queue. **Grouping and the user's energy** (review of PR 130): when the grouping job merges the files of one track into another, the emptied track's non-rekordbox rows move to the track that stays unless it has one of its own for that source, and what didn't move is deleted, both outside the operation log. So a `user` energy is kept only if the track that stays has none of its own; otherwise it is lost. An Undo of the key press that set it is then refused (its row is gone), or, if the row moved, changes the track that stayed. Which energy should win, or whether the move should be logged, is not decided. |

"Use this file instead" (1cB-22) logs only its `file_choice` rows; the track's `recording_file.role` follows from the ranking, which runs as the action returns and as its Undo returns (`ops::undo_for_user`), so the lists are right at once and the roles are never part of the log. **Derived columns** (one list, `ops::DERIVED_FIELDS`: `library_track.source_status`, which follows the linked file, `relink.audio_hash`, `relink.file_key` and `relink.file_id`, `recording_file.role` and `recording_file.match_confidence`, the ranking's, and `file_choice.blake3`, which follows a retag of the chosen file): something outside the log keeps them current, so undoing an insert doesn't count a change to one as "changed since" (1bE-6, 2026-10-13), and undoing a set of one leaves it as it is (1bE-9, 2026-10-16: a merge of two Library tracks moves files, which start over in their new track, and its Undo ranks them again; "Same track" and a split move files the same way, 1bE-2, and no other operation sets one); a file an Undo moves back starts over in its track too (role `undecided`, ranked again). `recording_file` is changed through the log only by sets (a merge, "Same track", a split), never by an insert or a delete, so the grouping's own inserts into it can't trip an Undo. The new track a split moves a file into is made outside the log, as the grouping makes tracks, in the split's own transaction (`ops::record_with_derived_first`): the log names it only as a value, never as a row, so a track the grouping sweeps is never a row Undo takes back. Track and file ids were reused until migration 0031, and these checks stay as a second guard: the Undo of a split is refused ("changed since") when the track the file left may be another one by now: none of the files that stayed holds what it held there, or the track by that id was made at another time; and the Undo of "Same track" or a split is refused when a file it moved isn't that file any more (another file has its id, or it holds other audio: the operation keeps what each moved file held) or is a Library track's file now (1bE-2, 2026-10-16). A merge of two Library tracks can be undone after a send, as a removal can; it can't be undone once the track that stayed is linked to another file than at the merge, or a file the merge moved is a Library track's linked file (an automatic follow is no user step Undo takes back first, and two Library tracks would end on one file): refused with its own reason (1.12, 1bE-9). |

## 4. Features

### Phase 0: Foundations

#### 0.1 Repo and architecture
- **Stack:** Tauri 2 + Rust + React/TS.
- **Bindings:** `tauri-specta` generates the TS bindings from the Rust types. Never hand-edit the generated files.
- **Database:** one writer connection plus a pool of WAL read connections. No global `Mutex<Connection>`.
- **Job queue:** typed (scan, read, hash, fingerprint, read_rekordbox, analyze, embed, convert, export), with priorities, progress events and cancellation, persisted in the `job` table. A job the last run left running starts again at the next start, and work that is due while no job is queued is asked for then (1cA-13). Every long operation goes through it.
- **Frontend state:** TanStack Query for server state, Zustand for UI state, and one route per workflow stage. No monolithic `App.tsx`.
- **i18n:** `i18next` for all strings, with a lint rule forbidding raw strings in JSX.
- **Theme:** tokens only, with no hardcoded colors in components.
- **Network gate:** one `net` module checks `service_optin`. A test fails if any other module makes HTTP calls.
- **Migrations:** append-only. A test fails if an applied migration is edited.
- **Write guard:** only the Library module gets a writable file handle (§5.6).
- **Suggestions:** every suggestion type carries a reason string. A test fails if one reaches the UI without it.
- **Complexity:** M. **Reuse:** musicmanager's DB layer patterns and its `fields.rs` single-source-of-truth pattern.

### Phase 1: MVP, your first Library
Each feature is tagged with its sub-phase.

#### 1.1 Multi-root in-place scan · 1a
- **What:** add any number of folders or drives. Each is indexed read-only, with incremental re-scans and an optional watcher per root. Every online folder is rechecked at app start and whenever its drive comes back; "Watch for changes" (off by default) adds live updates while the app runs (owner, 2026-09-30).
- **Stages:**
  1. A walk with stat only, so the UI fills in within seconds.
  2. Tags and audio properties.
  3. Hash and fingerprint as background jobs, visible tracks first.
- **Unchanged check:** (size, mtime, file-id), made inside the walk before it updates a row. A different size, or a different file id together with a different mtime, is a change: the stages redo the file. On an mtime-only change, or a new file id with the same size and mtime (restores, sync tools and shares with unstable ids), the walk compares a **partial hash** (`file.partial_hash`, stored by the hash stage): the file's size, every byte of metadata (all bytes outside the audio) and the first and last 64 KiB of the audio. Equal means the content is the same, so the row's mtime and the stages' recorded mtimes move on and nothing is redone; different, or none stored (unknown format, Ogg, over 4 MiB of metadata), means changed. A same-length edit in the middle of the audio, away from both ends, is the known blind spot. rekordbox bumps mtimes (§5.1); a tag rewrite still counts as a change, since the metadata really changed. These comparisons are the only reads a walk makes of a file (1aC-1, 2026-09-29).
- **Offline volumes:** they stay in the index, greyed out ("Drive not connected"), and their files stay present. A file is set to `present = false` only when a walk could list its folder and the file wasn't there, never under a folder the walk couldn't list; it's never dropped. Drives coming and going are noticed through WM_DEVICECHANGE, and a walk stops if its drive is swapped mid-walk (same letter, other serial or GUID). A cloned backup the library knows is never taken for the original: plugged in alone, it keeps its own identity and the original's folders show offline (1aB-9, 2026-09-29).
- **A folder is scanned when it is added,** from whichever screen adds it: the add command queues the scan itself (1aG-10, 2026-10-02). "Scan again" on a folder's row scans it on request.
- **After a kill or crash** (1aG-10, 2026-10-02): a job the last run left running is put back in the queue at startup and runs again from the top, if its kind can (the scan stages, quality checks, waveforms, grouping, relink, attach, a rekordbox read); any other ends as failed. Left as it was, such a job blocked its scan stage for good. Send jobs are still dropped at startup (1.9). A job put back does only what is still due, and that is all the resuming there is (1cA-13, 2026-10-12): no job keeps a cursor. A job the user cancelled before the kill is ended as cancelled, not put back. At startup, once the queue is up, each stage that can have work due with no job queued is asked once and queues its job if so (the hashes, grouping, the fingerprints, quality, matching, deciding, the file roles, the search index, the waveforms); the reads come from the catch-up scan every online music folder gets at start. Relink and attach are not asked: an app that dies after a rekordbox read ends but before their jobs are queued waits for the next read.
- **Fingerprint progress is the whole library's** (DOGFOOD C1-2, 2026-10-10): a fingerprint job over every due file counts the files settled before it started as done, so a second pass for files that became ready later carries on from the first's figure instead of starting at 0%. The figure can still dip when a scan finds more files. A job for named files (the tracks on screen) reports on those alone.
- **Scanning rules:** see §5.5 (skip AppleDouble files, read tags leniently, sniff the format, flag broken files).
- **OneDrive placeholders:** reading one triggers a download. Detect the placeholder attributes and skip unless the user opts in. Onboarding explains the risk (4.2).
- **Target:** first results in under 5 s on 100k files, and a full index without fingerprints in minutes.
- **Measured** (2026-09-30, 1aC-7 and 1aC-12; 100k generated files on the owner's laptop, release build, Windows Security on): first results in 0.3 s. Finding and reading every file: 6.7 min on a never-read tree, 32 s once the files are cached. Reading uses up to 4 threads shared with fingerprinting, and the cold time is disk plus antivirus on first open; serial reading took 15 min. Hashes take about 1 min, a rescan with nothing changed 12 s, peak memory about 100 MB.
- **Complexity:** M. **Reuse:** `reconcile.rs`, the `walkdir` scanning, tag reading.

#### 1.2 Read your rekordbox collection · 1a
- **What:** read the rekordbox 7 collection without changing it, and match each entry to a file in the music folders. rekordbox entries whose files are in no music folder are listed, with an offer to add their folder.
- **Carried to the track (with provenance):** BPM, key, beatgrid, cues, play count and last played, rating, color, comments, My Tags and playlist membership. It follows the track, not just the file.
- **When:** at first run, after each send (1.9), and on demand. This is also how rekordbox's analysis of new Library tracks comes back.
- **Sources:**
  - **Always:** the XML export. The user saves it via File → Export Collection, and the app asks for the file or watches for it.
  - My Tags come in via the "Add My Tag to the comments" setting.
  - **Optional:** gig sticks (`export.pdb`).
- **Relink** (paths go stale when DJs change computers or accounts). Try in order:
  1. The path is still valid.
  2. Filename + duration (±0.5 s, read from the file). The XML's `TotalTime` is truncated to whole seconds, so a `TotalTime` of T matches a file lasting from T − 0.5 s up to (not including) T + 1.5 s (1aC-3, 2026-09-30).
  3. A unique duration within the candidate set: the files directly in the folder the Location's folder still names, plus the folders its neighbours (tracks from the same rekordbox folder, matched by path, filename + duration or a gig stick, or confirmed) were matched into; at most 50 files, and none of unknown duration. Accepted only when a title tag agrees with rekordbox's Name (featuring credits, case, punctuation and spacing folded; bracket contents kept); otherwise **probable**, like step 5 (1aC-5, 2026-09-30).
  4. The acoustic fingerprint (1.4). A track whose file is gone has no audio to fingerprint, so the evidence is the file record the scan kept when the file went (the one at the Location, or the one of a confirmed relink): a file nobody else holds with the same `audio_hash` is accepted as the same audio (only while that file's hash is current: a file that changed since it was hashed isn't trusted; and the gone file's own hash and fingerprint count only if they were current when it went). Failing that, another file of the gone file's track that is on disk (on a drive that isn't plugged in too, as for the same audio), on grouping's own current answer for the two files: a stored duplicate pair of the two, both files decided under the current rules and sitting in the track with the audio they hold (the gone file: held when it went), the mate's hash current. Accepted only when it lasts within 1 s of the gone file (the entry's cues and grid are positions in time, so a mate of another length, or where either length isn't known, is **probable** at most) and a title tag agrees with rekordbox's Name; otherwise **probable**, like a fingerprint duplicate: grouping compared the two files' names, never rekordbox's. A mate overwritten since, one due to be decided again, and one that only shares the track (never compared with the gone file, or kept there though the rules no longer call it a duplicate) aren't matched. Two limits: once the mate has been decided again while the gone file is away, their pair goes with that decision; and every new version of the grouping rules ends this for the files already gone, which can't be decided again. The fingerprint duplicate is then what remains (1bC-7, 2026-10-12). Failing that, the one fingerprint duplicate among all files lasting within 1 s of it, accepted only when a title tag agrees with rekordbox's Name (a Clean and a Dirty cut fingerprint alike), otherwise **probable**; a duplicate another track holds still counts, so the one left over isn't "the one". Two rekordbox entries never share the one file that's left. A drive that isn't plugged in is never taken for gone files: step 1 handles it. A match is never made on a partial comparison: a track waits while a file of about its length hasn't been fingerprinted yet, and one relink run compares at most 20,000 fingerprint pairs (it runs on the database's one writer; about 0.8 ms a pair for five-minute tracks in a debug build, measured in review), tracks with the fewest candidates first, leaving the rest undecided for that run and counted in the log. A waiting or undecided track still lays claim to every file of about its length, so none of them is given to another track meanwhile (1aD-1, 2026-10-01).
  5. Filename only: the only file with that name, counted over every file, and wanted by no other missing track. A file whose known duration doesn't fit `TotalTime` (step 2's window) isn't guessed: the same name at another length is more likely another cut; an unknown duration on either side doesn't block it. Always **probable**, and queued in Review as "rekordbox match uncertain" before any rekordbox data is attached (1aD-2, 2026-10-01).
  6. A connected gig stick as a recovery source.
  
  **Never match on size:** rekordbox rewrites tags, which changes the size, and the XML's `Size` can be stale (§5.3). Use `audio_hash` as a confirming check where available. Whatever is left is listed as "missing" with its last known path.

  **Every relink run decides steps 1–5 again from scratch**, so the result depends only on what's on disk and in the rekordbox snapshot, never on earlier runs: running again, or reading rekordbox again, with nothing changed gives the same matches. Only a confirmed relink (and, later, a gig-stick match) is kept between runs, and what the user said is not an entry's file.

  **The audio a match was made to:** a confirmed relink records the matched file's `audio_hash` (so will a gig-stick match). If the file later holds other audio (replaced under the same name), a confirmed relink is kept and still holds its file, but counts as probable, with no rekordbox data attached, until the user confirms again (owner, 2026-09-30); a kept gig-stick match is dropped and decided again. A tag-only edit changes nothing, and a hash that's missing or not current means unknown, never changed; only a current hash is ever recorded.

  **Confirm, "Not the same", withdraw** (1bE-6, 2026-10-13; `relink::decide`). A probable match waits in Review (1.12) until the user answers; each answer is one undoable operation, and a relink run follows it and its Undo. *Confirm* stores the confirmation (above); confirming again after the audio changed records the audio of now. *Not the same* stores that the audio the file holds is not that entry's: no run matches the entry to a file holding that audio again in steps 2 to 5, wherever the file is now (moved, renamed, its music folder added again), and a kept gig-stick match to one is dropped. Step 1 isn't affected (a file at the Location's own path is the file rekordbox itself opens, and is never probable). The step that would have made the match makes none for that entry, the entry goes on through the later steps, and another file may be proposed: a new item. The refused file still counts wherever files are counted (two files with one name are still ambiguous), so saying no can only take a match away. A file encoded again holds other audio, and is asked about again. Confirming takes back a "not the same" about that audio, and "not the same" takes back the confirmation of that file; every other decision about the Location stays. Each answer and its rows of the snapshot are written in one transaction. *Withdrawing* a confirmation deletes it, and the entry is decided again from scratch; the Details panel offers it for a Library track whose entry is trusted on its linked file with a confirmation standing (`TagSources.confirmed_entry`, 1cB-17), and it is what Undo of a confirmation amounts to. The entry's rows in the snapshot follow each answer at once (confirmed: trusted; not the same: no match; withdrawn: probable again), so Review is right before the relink run ends; that run decides them again.

  **Among files that are equally right** (exact copies that fit in step 2, 3 or 5, or the candidates of one step-4 rule), the track's best file is matched, else the lowest file id; and the file a Library track is linked to instead, wherever a match to it gets the same trust (1bE-10, 2026-10-12). A Library track whose linked file is on disk is sent as rekordbox's entry while the entry is matched to its linked file, or to a byte-identical copy of it (1.9), so a copy that turns up later, and ranks ahead, can't pull the entry off it. It is a tie-break only: equally right includes equally trusted. Steps 3 and 4 trust a match on the file's own title tag and length, so being linked never turns a match that would be trusted into a probable one, or a probable one into a trusted one, and an entry none of whose candidates is linked gets the file it always got. Relink itself never changes a Library track's linked file; the step that follows it in the same job does (1.8).
- **Skip what isn't a track:** deleted rows, rekordbox's demo tracks and samples, the "CUE Analysis Playlist", and streaming entries, which are shown as "streaming, no file" (§5.3). Streaming tracks are out of scope beyond that: they're never linked, sent or checked in the behavior check (owner, 2026-09-29).
- **Parsing:** see §5.3.
- **Complexity:** M, plus relink (M).

#### 1.3 Start your Library · 1a

  - **Start from rekordbox (main):** your whole collection or chosen playlists become **linked** Library tracks (1.8). There are no new rekordbox entries, no re-encoding and no file writes, and the Library looks like what you already play. Their duplicates and problems queue in Review (1b).
  - **Start fresh:** an empty Library, for new DJs, DJs switching software, or a clean start. Tracks you add are linked to their files where they are.
- **Fragile locations:** a Library track whose file lives in Downloads, a temp folder, an external drive or a network drive (owner, 2026-10-01) gets a visible warning with its reason ("this file is in Downloads; if you clear Downloads, the track goes missing"). #### 1.4 Acoustic fingerprinting + duplicate grouping · 1b
- **How:** exact blake3 or audio-hash matches are the fast path. Otherwise, index fingerprints by blocks to find candidate pairs, compare them, and group.
- **Decision rule:**
  - **Duplicate:** matched coverage ≥ 90% on *both* files and a difference score ≤ 4.
  - **The version check (1.5) can veto** a merge, because Clean vs Dirty fingerprint as 100% identical.
  - **One-sided coverage** (a Radio Edit found inside an Extended mix) means a **cut**: link it, don't merge. Unless the inner file is a cut-off copy (verdict `truncated`, 1.6) that begins where the other begins, under the same names and version words: then it is a duplicate, and the best file is the whole one (1bC-6, 2026-10-11).
  - **Low or no coverage:** names decide whether it's a rework link.
  - **Two Library tracks are never merged by the job** (owner decision, 2026-10-11). When two tracks that are both in the Library turn out to be the same recording (rekordbox had two entries for it, or both were added before their fingerprints were compared), they stay two tracks and Review shows one item for the pair. The user decides there: keep both, or merge into one, choosing which stays; the crates of both then hold the one that stays, and the other goes on the list to remove in rekordbox. Nothing in a crate or a send changes before that. Outside the Library, duplicates merge without asking. A copy outside the Library that is the same recording as both is part of the same item: after a merge it joins the merged track; after "keep both" it stays a track of its own and isn't asked about again (owner decisions, 2026-10-12; 1bE-9; how the two actions work is in 1.12). With three or more Library tracks that are the same recording, a merge folds all the others into the one the user picks, and "keep both" keeps them all (owner decision, 2026-10-16).
  - **A decision sticks.** "These aren't the same" (a split) and "keep both" are remembered, so a later run doesn't merge the pair again or ask again. A pair the rules send to review stays apart until the user decides. A decision names what the two files hold, not the files, and covers the two tracks: the user is asked once per pair of tracks, never once per pair of files (`grouping_decision`, §2). It's kept for every pair of audio between the two tracks, so it still holds when the file it was made on is overwritten or its music folder is removed. "Apart" for two files that already share a track moves neither (relink then no longer takes them for duplicates of each other): taking a file out of a track is an action of its own, the split in Review (1.12, 1bE-2), which moves the file into a track of its own and remembers "apart". A merge of two Library tracks (1.12) is not a remembered decision: it moves the files, and its Undo moves them back, so the pair is asked about again.
  - **A track is files that are duplicates pair by pair** (1bC-1, 2026-10-11). A set of files joined by duplicate pairs merges only if every pair in it is a duplicate; one stored pair that is a cut, a rework, a review or different, and nothing in the set merges: its duplicate pairs go to Review (`set_disagrees`). A pair in such a set that nobody decided is decided first (compared directly where nobody compared the two), and the set waits until it is. A set also waits, and never merges, while one of its files is due to be decided again, so a tag rewrite on one file doesn't release a held set. A file that isn't on disk keeps its track and takes no part: nothing can be decided about it, so it holds no set back, and a duplicate pair of its whose files are in two tracks waits for it to come back (`waiting`, not shown in Review). A set of more than 50 files holding several kinds of audio is held as if it disagreed. Files with the very same `audio_hash` are together without any of this.
  - **A merge is never undone by the job.** A new file or a retag never splits a track; only a file that holds other audio than it joined with leaves: its `audio_hash` changed, or, for a file with none, its `blake3` (so a file with no `audio_hash` leaves on a tag rewrite, and is decided again). A file whose audio changed is not decided, and not asked about as another file's partner, until its fingerprint is of what it holds now: nothing is decided on the fingerprint of audio a file no longer holds. Because merges are kept, a set whose pairs disagree can come out differently depending on the order its files were decided in (two files that merged before anything was stored about a third stay one track), and a fresh database may differ from an old one there. A run over an unchanged database changes nothing, the user's decisions and links included.
  - **The full table** (every combination of audio and names, its outcome and its reason) is in the `grouping::rules` module docs (1bB, 2026-10-11). It settles what the lines above leave open. Files with the very same audio (the same `audio_hash` or `blake3`) are always duplicates, whatever their names say. The same audio under another title is a duplicate, and says the names differ. "One-sided" is at least 90% of exactly one file found in the other, over every alignment, with a difference score ≤ 4. A link made by names alone needs the artists to agree. A file's version labels are those of its title tag and its file name together; with the audio matched, two files whose labels differ by a cut are linked, never merged, and by a rework go to review, whatever their titles. As a last guard, two files with a full audio match are merged without asking only if their names carry the same version words: every label word the parser knows, in brackets or not, anywhere in the title tag or the file name, counted per file (the file's artist is set aside only where a name spells the whole artist out). If the version words differ, a pair the table already links as cuts stays a cut link, and any other goes to review. Identical audio still merges whatever the names. "Original" is no version word here. Not seen: a label word fused to another word ("VeloDirty"), a hyphenated spelling in the middle of a name ("Re-Fix"), a version given by a folder further up than the one a file sits in, a folder word for a file that sits directly in a music folder (the music folder's own name isn't seen), and, in a file with no title tag, a file name whose second part is only a label ("Velo - Radio Edit.mp3" stays artist and title, though its label word is still counted). A pair whose fingerprints were never compared goes to review if its names are the same, and is otherwise decided as if it shared no audio; so before asking, the grouping job compares directly every pair whose names are the same or where one is a mashup naming the other as a part. It finds those pairs by title; a title more than 50 files share ("Intro", "Track 01") is narrowed to the files that also share an artist, and where that is still more than 50 the pairs are skipped: not compared, not stored, left apart, and counted in the run's result. A title with no letter or digit brings no files together.
- **Speed-up:** a short-window fingerprint (e.g. the first 120 s) may be used **only to find candidates**. Duplicate and cut decisions always use full-track fingerprints: one E3 pair only diverges after about 2 minutes.
- **Cost:** measured in 1aB-7 (release build, one core, decode included): about 0.3 s (WAV), 0.4 s (FLAC) and 0.6 s (MP3 320) per minute of audio, so 1.5–3 s for a five-minute track. A large real library (thousands of tracks) takes 1–2 hours of background time on 4 threads. Runs in the background at below-normal priority on a shared budget of at most 4 threads, visible tracks first. The short-window candidate pass is the lever if big libraries need it.
- **Risk:** false merges. Mitigated by version awareness and by always letting the user split a group.
- **Complexity:** L.

#### 1.5 Version awareness · 1b
- **What:** never merge different versions. Link them instead, as one of two kinds (§1.2):
  - **Cuts:** Original ↔ Extended / Radio Edit / Club Edit / Short, Clean ↔ Dirty, Intro / Outro / Intro-Outro, Quick Hit, a plain "(Edit)", and Remaster (with or without a year; two remasters of different years are two cuts, and one that gives no year is the same as any; 2026-10-11).
  - **Reworks:** remix (per remixer; a named mix, "(Some Name Mix)", is a remix by that name unless the words are a cut's name; a "name" made only of ordinary words such as Main, Album, Vocal or DJ is no one's name, so that bracket is not recognized and the pair can't be told), VIP, flip, bootleg (including "(Re-Edit)" and a named edit, "(Some Name Edit)"), rework/refix/reboot, dub, cover (labeled "cover"), live, alternate arrangement, instrumental, acapella (neither is a stand-in for the full track), and mashups (`A x B`, linked to each source they contain).
- **Signals, combined:** the version parsed from title and filename; fingerprint coverage (full both ways = duplicate candidate, one-sided = cut, none = rework or a different song); and credits. The fingerprint alone decides nothing across versions. When signals disagree, the pair goes to "needs review", with the reason shown.
- **Rules from the E3 labels** (all in the test corpus):
  - Length decides nothing.
  - Version words can be the real title (a title that really ends in "(dirty)"). Compare against the other file; never strip blindly.
  - Remixes are often credited only to the remixer.
  - The same title can be different songs, even as remixes.
  - Mashup part names can match unrelated tracks.
  - **Identical tags can hide a different recording**, so the fingerprint can veto a name-based merge. A partial match between files with identical tags goes to review, with both files playable.
  - Strip store and rip junk: HTML entities (`&#40;Original Mix&#41;`), Beatport ID prefixes (`10000001_`), and site-name prefixes or suffixes such as `RipSite.example - ` or `[ example-ripper ]`.
  - Naming conventions vary across pools (each record pool has its own) and bootlegs (`(@handle edit)`, `[Artist Flip]`). Users can suggest patterns through issues.
- **Complexity:** M–L. This is the parsing library the rest of the app leans on, so it needs a large test corpus. The 43 E3 labeled pairs use real library names and aren't published, so they run as a **local** corpus; CI uses synthetic cases derived from the same patterns.

#### 1.6 Quality verification · 1b
- **Verdicts:** `ok` / `low bitrate` / `suspect transcode` / `truncated` / `broken`. A `clipped` verdict is held back (owner decision, 2026-10-10): nothing measures clipping yet, and loud masters clip on purpose.
- **How:** FFT spectral cutoff (the highest frequency within 50 dB of the 2–8 kHz level, from a 60 s sample: the 60 s starting 30 s in, to skip intros and fade-ins, or the first 60 s for a file under 50 s), decoded vs header duration, and decode errors.
- **Thresholds:**
  - MP3 at ≥256 kbps with a cutoff below 17 kHz → `suspect transcode` ("this 320 was made from a ~128 kbps source").
  - 17–19 kHz → shown as "possibly lower quality", not flagged.
  - Lossless with a cutoff below 19.5 kHz → `suspect transcode` ("this FLAC/WAV was made from an MP3").
  - **Bitrate of a lossy file, two levels** (owner decision, 2026-10-10). Below 192 kbps → `low bitrate`: seriously bad, flagged, and the app warns before such a file is added to the Library. From 192 kbps up to full quality → shown as "could be better", not flagged: a note that a better file exists somewhere and a candidate for "Find a better file". Full quality is 320 kbps; for AAC it is 256 kbps, the rate stores sell (foreman's default, the owner may overrule). A lossless file has no bitrate level.
- **How the verdict is reached** (1bB-6, 2026-10-11; the table is in the `quality::verdict` module):
  - One verdict per file, the first that applies: `broken`, then `truncated`, then `suspect transcode`, then `low bitrate`, then `ok`. Everything else that applied is kept as a list of findings.
  - **Rounding room.** Files store an average bitrate, so the lines sit a little under the nominal figures: low below 190 kbps, full quality from 318 kbps (AAC from 240 kbps, because store AAC is variable), and the transcode check from 254 kbps.
  - **Which codecs.** Vorbis, Opus and WMA use MP3's bitrate lines. AC-3, E-AC-3 and Musepack get no bitrate level: no line was set for them.
  - **`truncated` by length:** the audio is shorter than the length the file states by more than 2 s and by more than 1%. An MP3 without a length header states an estimate, so such a file can be flagged wrongly; "Keep anyway" covers it.
  - **A transcode needs room to show:** a file whose sample rate can't carry audio above the cutoff line (32 kHz and below) is not flagged.
  - A few decode errors in a complete file are a note on an `ok` file, not `broken`.
  - Without a measurement only what the file's header shows is judged (bitrate, a read that failed); such a file is never called `ok`.
- Suspect files are reviewed in Review (1.12): "Keep anyway" handles genuinely rolled-off masters, and "Find a better file" sends the track to the wishlist.
- **Complexity:** M.

#### 1.7 Best-file picker · 1b
- **Ranking** (`best_file`): each step only breaks the ties of the steps before it. In order: **the user chose this file** ("Use this file instead", 1.11; 1cB-22, owner decision 2026-10-28; decisive, only for a track outside the Library and a file on disk, so the reason is "you chose this file" and a chosen file that is gone has no say); the file is on disk (a file on an unplugged drive is); the quality verdict (ok, not checked, flagged, truncated, broken; low bitrate and suspect transcode are one tier); plays in the DJ app (foreman's default, the owner may overrule); the measured cutoff, not the header bitrate; fewer decode errors; format (owner decision, 2026-10-11): lossless over lossy, then among lossy files full quality for the codec first (foreman's default, the owner may overrule), then FLAC, WAV and AIFF, float WAV, ALAC, WavPack, APE and MP3, AAC, Vorbis, Opus, WMA, then header bitrate; tag completeness; embedded art; whether rekordbox knows the file; location (scan folder over Inbox, internal over external over network, folder added first; whether a drive is connected right now does not count in the stored best file, so plugging a drive in or out never moves it); last, the lower file id. Every suggestion states its reason.
- **Audio and tags are picked separately.** The best file decides only the audio. Each tag and the cover art come from the best-ranked of the track's files that has a value, including extra files; there is no majority vote. When files disagree, the app picks one by rule and Review shows the disagreement.
- **Linked tracks:** their audio *is* the file rekordbox uses, so in the MVP a better duplicate shows as **"Better file available"**, with its reason ("FLAC vs your 320 MP3"). A file counts as better only for its audio or for being there: it is on disk when the linked file isn't, its quality verdict, whether the DJ app plays it, the measured cutoff, decode errors, or its format. A copy that only has more tags, more art, a rekordbox link or a better place is not a better file: tags and art are picked per field, apart from the audio. The linked file is pinned: a better file never moves the link, and neither does grouping, relink or a send. A link moves on its own in one case only, when the linked file is gone from disk and the very same audio is on disk (1.8, "A Library track follows its file"). The only other way a link moves is the user's own switch of a gone linked file to another copy, in Review (1.12). The **Upgrade** action arrives with managed copies (2.6). Chosen tags reach rekordbox only via the XML, because the file is read-only.
- **Resolving changes DB state only.** Nothing on disk changes.
- **Complexity:** M.

#### 1.8 Add to Library · 1a
- **In the MVP every Library track is linked:** it points at an existing file. For tracks rekordbox knows, that's the file rekordbox already uses, so nothing changes in rekordbox and cues and history stay safe. For tracks rekordbox doesn't know, the next send adds them at their current Location.
- **Which file** (1aD-6, 2026-09-30): the file of a trusted rekordbox match; otherwise the track's best file. A probable match is never the file linked. **A track whose only rekordbox match is probable can't be added by hand** until the match is confirmed in Review, or answered "Not the same" (1bE-6, built 2026-10-13; owner decision, 2026-10-02): linked to its best file it would be sent as a new track, beside the rekordbox entry that is probably its own, a second entry without the cues. The add refuses with its own reason, and All music greys out the row's "Add to Library" with the reason on the row. A track that also has a trusted match is linked to that file as before. The add is refused when the track has neither, or when that file isn't on disk; such tracks wait in the Missing list (1.3). **Which file is "best" when one is gone** (owner decision, 2026-10-11; 1bC-4): the ranking (1.7) puts a file that isn't on disk below every file that is, so a track rekordbox doesn't know, whose better copy was deleted, is added linked to the copy that is there. There is still no fallback for a trusted match: when rekordbox's own file is the one that's gone, the add refuses, because another file would become a second rekordbox entry without the cues. A file on an unplugged drive counts as on disk (unplugged isn't missing, 1.1): its track can be added and shows no "File missing". Adding a track that's already in the Library changes nothing.
- **Read-only:** the file stays where it is and is never written. Tag fixes reach rekordbox only via the XML (on first import, XML values win over file tags, §5.2).
- **Carried over:** rekordbox's data (1.2) and the best tags gathered from all the track's files (1.7), sent through the XML.
- **Fragile locations** are warned about (1.3).
- **Durability:** "file missing" when the file disappears. An in-app delete asks for confirmation, can be undone, and drops the track from the next send.
- **A Library track follows its file** (owner decisions, 2026-10-12; 1bE-10). When the linked file is gone from disk and a file with the very same audio (an equal `audio_hash`, current for the new file and current for the old one when it went) is on disk in any folder the app scans, another drive included, the track's linked file moves to that file on its own. Nothing else moves a link on its own in Phase 1, and it only ever moves to the same audio: another encode never follows, even one of the same length and title. That is a "Clearly best file" item in Review (1.12), the Library list shows the track's file as missing meanwhile, and the track is still sent as rekordbox's own entry (1.9). The rules:
  - **Gone means gone.** Only a file a walk looked for and didn't find counts. A drive that isn't plugged in is never taken for gone files (unplugged isn't missing, 1.1). While the linked file is on disk nothing moves, so a file that comes back later moves nothing back. A file that was moved back (the new place is gone, the old one is there again) is a move like any other: the track follows it back, and a track rekordbox knows is sent as its own entry again.
  - **A file of the track itself.** The new file is one grouping has put in the Library track's own track (files with the same `audio_hash` are one track, 1.4), so no file changes track. A file grouping keeps apart isn't followed.
  - **One track, one file.** A file a Library track is linked to is never followed to, and when two Library tracks hold that audio (the same recording twice, 1.4) nobody follows.
  - **The automatic follow never changes which rekordbox entry a track is sent as.** The hold is about a second entry and about a change of entry, nothing else. After relink has committed, the follow looks at the rekordbox entries matched to the new file (whatever the match: trusted, probable or confirmed) and asks the send what the track is sent as today and what it would be sent as linked to the new file. With two or more entries matched to the new file, nothing moves, whichever of them a send would pick. When the track is sent as one entry today and would be sent as another, or as none, on the new file, nothing moves: a track rekordbox knows follows only where relink has matched its entry to the new file and trusts the match, and is then sent as that entry, with rekordbox's old `Location` (the check before a send lists it, 1.9; there is no other notice). The link follows when the track is sent as the same entry before and after, as no entry before and after (a track rekordbox doesn't know: the next send adds it at the new place), or as no entry today and, on the new file, as the only entry matched to it: that is a file moved back to its entry's path, and a track rekordbox didn't know whose moved file rekordbox has since learned. Two more holds: a follow never takes a file that the entry another Library track is sent as is matched to, and a track that would go out as new doesn't follow while a file of its track is the probable match of an entry, as an add is refused there. Where nothing moves the track stays a Review item: a switch that changes rekordbox's entry is the user's choice (1.12).
  - **When it runs:** as the second step of the relink job, after relink has committed and in transactions of its own: after the hash stage, after every grouping run and after every read of rekordbox. Never while the user waits, and it reads only the database: the job asks where the drives are once, before it takes the database's writer, and both steps work from that answer, so no other write ever waits on a drive. Running it again changes nothing.
  - **In the log, skipped by Undo.** Each follow is an operation of its own that the app made ("automatic"). The Undo button never lands on one: the next Undo takes back the user's own last action. Undoing an earlier action on the same track (its add) takes the follows made since back with it, all or nothing; a follow on another track stays. They are taken back as one net change, not step by step: undoing the add deletes the track without first linking it back to the file it followed from, so it still works after the old music folder, and with it that file's record, has been removed from the app. Undo is refused, changing nothing, when something else changed the link since, or when a value it has to write back no longer exists.
  - **The old file back beside the new one** (1bE-11, 2026-10-16; until then a known limit of 1bE-10): rekordbox's entry is matched to the file at its own path again (1.2, step 1), and the link, whose file is on disk, stays. The track is still sent as that entry, because the old file is a byte-identical copy of the linked one (1.9, "A byte-identical copy's entry"). **Known limit:** only while the two files are byte-identical. Once rekordbox has written a tag into its file (§5.1), they hold the same audio but not the same bytes, and the track goes to rekordbox as a new one, which the check before a send lists ("rekordbox has another file of the same track").
- Managed copies (converting, clean tags written into a new file, upgrades) are Phase 2 (2.6).
- **Complexity:** S.

#### 1.9 Send to rekordbox (XML) · 1a
- **What:** write the Library and its folders as rekordbox XML:
  - **COLLECTION:** tracks, per rule 4.
  - **PLAYLISTS:** two top-level folders, `Crates` and `Playlists`, holding their trees as NODEs.
  
  The user then imports it through rekordbox's `rekordbox xml` sidebar.
- **XML writer rules** (the behavior behind them is in §5.2):
  1. **Every attribute of every track sent, every time.** Fill each with rekordbox's current value from a fresh read, unless the app means to change it. Never omit, never default. The only exception is the analysis fields in rule 3.
  2. **Read → merge (1.10) → send in one step.** Every send's review merges first, and the go merges again before it rebuilds the send (1.10, "Merged before every send"; 1cB-3). Tell the user not to play or edit in rekordbox from the export until the import is finished: the values sent come from that export, so anything changed in rekordbox after it is overwritten by a Yes.
  3. **Analysis fields** (`TEMPO`, `POSITION_MARK`, `Tonality`, `AverageBpm`) depend on the case:
     - **(A) The track is already in rekordbox at this Location:** omit them.
     - **(B) A managed copy at a new Location** (Phase 2, 2.6): send them deliberately, carried over from rekordbox's entry for the old file.
     
     **Confirmed by gate test T3** (2026-09-28, rekordbox 7.2.19): omitting them keeps rekordbox's key, BPM, grid and cues. **Never send the app's own BPM or key estimates for a track rekordbox already has**: a Yes re-import loads any `Tonality`/`AverageBpm` the XML carries, over rekordbox's analysis and out of step with its grid.
  4. **COLLECTION holds every track that a sent playlist or crate references, plus new tracks, each with every attribute (rule 1).** Gate test T1 failed (2026-09-28, rekordbox 7.2.19): a playlist entry only resolves if its track is in the same XML's COLLECTION; other entries are dropped silently, whether keyed by TrackID or by Location. So playlists-only sends are impossible. To keep a send small, it may carry only the playlists and crates that changed plus their tracks. Every track already in rekordbox raises the Yes/No dialog (or the user ticks "Don't ask me again"), so the checklist states how many dialogs to expect.
  5. Write `Location` fully percent-encoded.
  6. **App-owned playlists live only under `Crates` and `Playlists`.** When a crate is renamed, moved or deleted, the next send lists the stale rekordbox playlists to delete by hand: only ones the app itself sent before. Something the user made in rekordbox is never listed, even inside those two folders.
  7. **Removing a Library track can't reach rekordbox via XML.** The app says so and lists what to remove.
  8. **Record `sync_base`** for every field sent.
- **How the writer applies them** (`rekordbox_write`, 1aE-7 to 1aE-10, 2026-10-01):
  - **Never analysis, for any track in Phase 1.** `AverageBpm` and `Tonality` are dropped from every track's values, and the writer can't write a `TEMPO` or `POSITION_MARK` at all. Case B arrives with 2.6.
  - **A known track that no sent crate or playlist names isn't sent** (it would only raise a Yes/No dialog). New tracks are always sent.
  - **`Location` encoding:** everything but ASCII letters, digits and `- . _ ~ / :` as uppercase `%XX`, read back with the reader before it's used. A new track's path is always written this way. **A known track's `Location` is re-encoded only when it's a drive path in rekordbox's usual shape** (`file://localhost/C:/…`), starting with exactly that prefix and escaping only characters rekordbox itself escapes, so the two spellings differ in escaping alone: that's the form the behavior check sent and rekordbox updated in place. In any other shape (a network or macOS path, a server or nothing where `localhost` goes, backslashes, an uppercase prefix, an escaped `/`, `:`, `.` or letter) it's sent back exactly as rekordbox wrote it, because re-spelling those is unverified (§5.2).
  - **TrackIDs are file-local.** A known track keeps rekordbox's; a new one is numbered above the highest TrackID in the whole last rekordbox read. Entries use `KeyType="0"`.
  - **A track that can't be sent is left out and reported with a reason code**, along with every entry naming it; the other tracks still go. That covers a missing file or Location (but not a missing file of a track rekordbox already has; see the next point), a value holding a character XML 1.0 can't carry (the value is never stripped or rewritten), and two tracks at one Location. A crate or playlist that loses every entry is still written, empty, and listed.
  - **A known track whose file is missing is still sent** (owner decision, 2026-10-01; found by Location, 2026-10-01), so a crate or playlist naming it stays whole: rekordbox's own entry goes back unchanged, every attribute exactly as rekordbox wrote it, `Location` included (not re-encoded), analysis fields omitted as for any known track. Relink never matches a rekordbox row to a missing file (it drops such a match on every run), so the entry is found by the linked file's own path instead: the one row of the newest rekordbox read at that `Location` (compared as relink compares a path: NFC, NTFS letter case). The entry at the linked file's own `Location` is this track's entry, whatever relink has made of it since: it is used when it is matched to no file, and when relink matched it to a file no Library track is linked to, such as another copy of the track that is on disk, or a look-alike elsewhere (owner decision, 2026-10-12; 1bE-10; until then such a track was left out of the send). The file relink matched it to is never what is sent. The path is the volume's mount point plus the file's path on it, with the mount point chosen by relink's own rule (where the volume is mounted now, or where it was last mounted only if no other known volume was), so a file on an unplugged volume whose drive letter another volume shares isn't looked up. This only echoes rekordbox's entry back at its own `Location`; it attaches nothing to any file, so it's no match in relink's sense. With two rows at that `Location`, a row matched (trusted or probable) to a file another Library track is linked to (that track sends it: one entry is never sent for two tracks, so the gone-file track is left out from the moment the other track is in the Library, and sent again once it is removed), a row kept from an earlier, incomplete read, a row two Library files lead to (it goes to neither), or no row at all, the track is left out with its missing-file reason, as above, unless a byte-identical copy's entry is used (next point). The track's `sync_base` is recorded as for any known track (rekordbox's own values), and its `last_sent_location` is rekordbox's `Location`.
  - **A byte-identical copy's entry** (owner decision, 2026-10-13; 1bE-11, 2026-10-16; `send_values::entries_of_copies`): a Library track whose linked file has no rekordbox entry by the points above (no trusted match on it; for a missing file, no entry at its own `Location`), while a byte-identical copy of it in the same track has one that no other Library track is sent as, is sent as that entry, whether or not a follow was involved: rekordbox's entry exactly as for any known track, its own `Location` (the copy's path) included, so rekordbox goes on playing the copy, keeps the cues and gets no second entry. The exact condition: the copy is a file of the Library track's own track, on disk, other than the linked file; the two have the same `blake3` (every byte), with the hash stage current for both (for a missing linked file: current when it went); exactly one rekordbox row is matched to the copy, whatever the match, and that match is trusted; of the track's copies exactly one is such a copy (two copies with an entry each: neither is used); and no other Library track is linked to the copy or is sent as that entry from its missing file's own `Location`. Otherwise the track is sent as before. A copy is a file of one track, and a track has one Library track, so no second Library track can claim the entry this way: one entry is never sent for two tracks. The same `audio_hash` with other tags isn't enough: rekordbox plays the copy, not the linked file, so the two must be the same file. Like the point above, it only echoes rekordbox's entry back; it attaches nothing to any file and moves no link. The follow (1.8), a switch in Review (1.12), the list of tracks to remove (rule 7) and a merge all ask the send, so they agree with it: after a merge, a staying track with no entry of its own is sent as the leaving track's entry when their files are byte-identical, and that entry isn't listed to remove.
  - **`Crates` and `Playlists` are always both written**, even empty. Two siblings with the same name (compared in NFC, ignoring letter case and trailing whitespace, §5.2), or a nameless node, refuse the whole send.
  - **Characters:** `& < > " '` are escaped, and tab, line feed and carriage return are written as character references, so a value reads back exactly.
  - **The file is read back with the app's own reader before it's written**, and written through the write guard to a new file beside the destination, renamed into place once complete.
  - **Rule 8** (`record_send`, 1aE-11, 2026-10-01): once the file is in place, each sent track's `sync_base` becomes exactly the fields written (a field sent before and not this time is dropped; a field with an open conflict keeps the base it had, or none, 1.10; 1cB-3), each with what it replaced in rekordbox (`sync_base.replaced`, §2; 1cB-19), each playlist written gets exactly the tracks it put in it as its rows of `sent_entry` (§2; 1cB-19) and, for a crate's playlist, which tracks it changed in rekordbox's playlist of that name (`sent_playlist.replaced`, §2; 1cB-3), and each sent track's `last_sent_location` and `last_exported_at` are set, in one transaction. All of it or none. The `Location` base is the string sent, which for a re-encoded drive path differs from rekordbox's own spelling, so 1.10 must compare `Location` by its decoded key, never as text. An analysis field is never given a base, whatever is sent. A send isn't in the operation log. Its new bases never take the row id of a deleted one (`sync_base` ids are never reused, §2), so removing a track can still be undone after a later send: the track comes back with the bases it had. Undoing the add of a track that was sent since is refused, changing nothing (the track is removed with "Remove from Library" instead).
  - **Rules 6 and 7, after a send** (`after_send`, 1aF-2, 2026-10-01): two lists computed from the database, so they never depend on a send having just happened. **Stale playlists:** a playlist or folder is listed only if the app itself sent it before (owner decision, 2026-10-01), a read has shown it in rekordbox under the top-level `Crates` or `Playlists` folder, the latest read still has it, and the app's tree no longer has it (names compared as the writer compares them: NFC, letter case and trailing whitespace ignored; a folder never stands for a playlist of the same name). Something the user made in rekordbox is never listed, even inside those two folders, and nothing outside them is. A stale folder is listed once, and only when everything rekordbox has inside it, at any depth, was sent by the app too, so its count is exactly what deleting it deletes; a folder holding anything the user made isn't listed, and the recorded playlists and folders inside it are listed one by one. "The app's tree" is the whole crate tree, not the subset one send carries, so an unchanged crate isn't stale; the app has no playlists of its own until Phase 3. What a send wrote is kept by `record_send` in the table `sent_playlist` (§2), in the send's own transaction and cumulative across sends: a path is marked seen once a read shows it in rekordbox and forgotten when a later read no longer has it (any read counts, including one of a different export, which can only list less), and a path never seen stays (that send may not be imported yet) but is never listed until a read shows it. The last read's names for the two folders (empty ones too) are kept as one setting, `rekordbox_playlist_tree`, written in the read's own transaction and replaced whole by the next read; an incomplete export (§5.3) keeps its tree too, since only its tracks can be missing. Until a read has kept them, the list says it wasn't checked. **Manual removals:** every track removed from the Library in the app that rekordbox still holds, whether or not a send ever wrote it (owner decision, 2026-10-02; before, only tracks sent before were listed, which in a Library started from rekordbox left out every track no crate named). A track that was sent is matched to rekordbox's tracks by the decoded `Location` it was sent to (a `Location` that can't be read back is matched by the read's rows matched to the track, and shows no path); it leaves the list once a read made after its removal no longer has it, and a read from before says nothing. A track that was never sent is listed while the latest read holds rekordbox's own entry for it, found through a trusted match to one of the track's files, and shows that entry's path; it leaves once a read no longer has the entry. With only a probable match, or no rekordbox entry at all, it isn't listed. **An entry a switch left behind** (1bE-7, 2026-10-13): when the user switches a Library track's gone linked file to another copy in Review (1.12) and the track then goes to rekordbox as another track than the entry it was sent as, that old entry is recorded (`replaced_entry`, §2) and listed here too, while a read holds an entry at its `Location` and no Library track is sent as it; so one entry is never both sent and listed. **An entry a merge left behind** (1bE-9, 2026-10-16): when the user merges two Library tracks that are the same recording (1.12), the entry the track that leaves was sent as (or, for a track a send wrote that no read has shown yet, the `Location` it was sent to) is recorded the same way, with the reason `merge`, and listed under the same condition; a track rekordbox never held leaves nothing to list. One entry is listed once: where a removed track is already listed at that `Location`, the entry isn't listed a second time. The track itself stays in the Library.
- **How a send runs** (`send`, 1aF-1, 2026-10-01):
  - **Two steps, each a job.** *Prepare* reads rekordbox's export again, always (a send never uses an old read), matches its tracks to files, merges (1.10, "Merged before every send"), and builds the **preflight** without writing a file. The merge is its only write to the database, and it stays whether or not the user goes: conflicts opened, updated or withdrawn, and the app's own values rekordbox's newer ones overtook taken in (derived from the three sides; the next merge would write them again). The matching and the preflight are one database job, so no other read can land between them and make a known track look new. A send job never runs in a later run of the app: every job names the run that queued it and does nothing in another, and one left queued or running is ended at startup, so a write only ever follows a click in this run. *Write*, on the user's go, builds the send again and refuses unless it is byte for byte the send that was reviewed, from the same read, of an export that hasn't changed on disk since. A preflight is good for one send; the next send starts with a new read.
  - **The preflight shows:** how many tracks are new and how many rekordbox already has (the Yes/No dialogs to expect); every track left out, with its reason; tracks rekordbox has that are sent although their file is missing; tracks rekordbox has that are sent with rekordbox's own `Location` while no file is at that path (the app paired the entry with a file elsewhere, and a send never changes a known track's `Location`, so rekordbox will still show "file not found"; the path is looked up on disk once, by the prepare step, after its database job; a track isn't listed when that can't be told (its drive isn't connected, or is a network drive, mapped to a letter or not; a network or macOS path; a lookup that fails for another reason than the file not being there); a track sent although its file is missing is never listed here as well; and the list is review information only: it isn't part of what the write checks, so a file that comes back before the go changes nothing about the go; DOGFOOD C1-9, 2026-10-10); new tracks sent without a `Kind`, because their file is in a format rekordbox isn't known to play (Ogg, Opus, WMA and the like) or one the app couldn't tell (they're sent as before; rekordbox may refuse them or not play them; DOGFOOD K13, 2026-10-10); Library tracks whose file rekordbox doesn't have while it has another file of the same track, and that aren't sent as that file's entry (a byte-identical copy's entry, above) (they can be sent; a second rekordbox entry results); every crate or playlist that will arrive with entries left out, with its count (entries of a crate's playlist in rekordbox that no Library track is sent as count too: the import drops them, 1.10; 1cB-3); how many fields of the tracks sent wait in Review → Conflicts, sent with rekordbox's value until they're settled (1.10; 1cB-3); how many tracks rekordbox has, sent with the export's values, have a file changed after the export was saved, with the list on request and a warning to export the collection again from rekordbox (the files are looked up on disk once, by the prepare step, after its database job; a warning only, which never refuses the go; 1.10, "Second channel"; 1cB-4); and a refused send, explained.
  - **An explicit confirm is needed** when a crate or playlist loses entries, and when the read couldn't store some of rekordbox's tracks (a Library track on such a track's file goes out as new, and a Yes in rekordbox overwrites that entry).
  - **Refused as a whole:** the writer's refusals above (same-name siblings, a nameless node) and **an incomplete export** (§5.3): it keeps rows from earlier reads, so some values would come from an old read. **An export saved before the last send isn't refused; the user is asked** (owner decision, 2026-10-10; from 2026-10-02 until then it was refused outright, DOGFOOD K16). Such an export can't show what that send put in rekordbox: if the send was imported, tracks rekordbox now has would go out as new and raise dialogs the review didn't count; if it never was, the export is as good as a new one, and the app can't tell which (it records nothing about imports). The export's modified time (what the checklist shows as "Export saved") is compared with the time the last send was recorded (the latest `last_exported_at` of any Library track or removed track, or `sent_at` of any sent crate); saved earlier, to the millisecond, the review asks whether a send has been imported into rekordbox since the export was saved. "No": the send goes ahead from that export, exactly as from a new export with the same content, and the review says it goes on that answer. "Yes": refused, with the ask to export again. No answer: the file can't be written. Saved at that millisecond or later, or with no send ever recorded: no question. The answer travels with that one go: it's kept only in that send job's own row, and no later send reads it, so the next send from the same export is asked again. A "no" lifts nothing else: a refusal still refuses, the explicit confirm is still needed where it was, and the write still rebuilds the reviewed send byte for byte. With no track to send and no crate or playlist, the send can't be started.
  - **One fixed file:** `tracklist-pro.xml`, directly in the app data folder, replaced on every send, so the app changes no bytes anywhere else (§6) and the user points rekordbox at it once. The checklist shows its path with "Copy path". There's no "show in folder": opening Explorer takes a process or shell call, which the write and network gates forbid.
  - **A failed send records nothing.** A failed write leaves the last send's file and every `sync_base` as they were; the go's own merge stays, as the prepare's does. The go records the send only while the open conflicts of the tracks sent, and every open crate membership conflict whatever its track, are the ones its merge saw: a conflict settled or reopened (a resolve, an Undo) between the merge and the record fails the go as "the Library changed", records nothing and puts the last file back (1cB-3). If recording the send fails once the file is in place, the last send's bytes are put back when that's possible; when there was no earlier file (or putting it back fails), the new file stays, unrecorded, and the send is reported as failed. A crash between the file going in place and the record leaves the same: an unrecorded file, which the next send replaces; nothing detects it at the next start. Before writing, the files a crashed send left behind are cleared (§5.6).
  - **What goes in:** every Library track (rule 4 decides which are written) and the crate tree: folders and hand-made crates, a crate's tracks in the order they were added. Smart crates wait for 3.3, and `Playlists` is written empty until Phase 3.
- **UI:** **Send to rekordbox** is the Overview's main button (1.13), shown once the Library holds tracks. It opens a guided checklist covering rekordbox's side: export the collection, review the preflight, write the file, point `rekordbox xml` at it (once), refresh, Import to Collection, Import Playlist, answer the dialogs (it says how many to expect). It warns not to play or edit in rekordbox from the export until the import is finished (the values sent come from the export). It is not a one-click sync.
- **Complexity:** M.

#### 1.10 Conflict detection & review · 1c
- **Three-way comparison per field** (app vs rekordbox vs `sync_base`):
  - only the app changed → send it
  - only rekordbox changed → pull it in
  - both changed → **conflict**
- **Conflicts queue:** **Review → Conflicts**, with side-by-side values. Keep the app's value, keep rekordbox's, or edit. Resolve in bulk ("take rekordbox for all ratings"). **Built** (1cB-1, 1cB-2, 2026-10-28; `conflict_review`, `ConflictsGroup`, `ConflictsPane`): every open conflict is listed, none hidden by default (owner decision, 2026-10-27), grouped by field; a row shows the track, the app's value, rekordbox's and the value at the last send, or "Never sent" for a field that has no base, each shown by the field's kind (stars for `Rating`, the color with its code, a date in the user's language, a file location without its percent-encoding; 0 reads "No value" for `Year`, `DiscNumber` and `TrackNumber`). For a title or an artist in dispute the Track column adds the linked file's name, since the name Review picks is one of the two values. Each row has "Keep app's", "Keep rekordbox's" and "Edit" (a field of the field's kind; "Save" is greyed out until the value fits it, and a date must be whole); a file location has no Edit, because the app holds no value of its own for it (the command refuses one too), and neither has a crate membership, which is only kept one way or the other (the command refuses that too); under the table "Keep app's for all N" and "Keep rekordbox's for all N" settle every open conflict of the field, N counting all of them, not only the loaded page; the command takes N and settles nothing if the number is not N any more (a conflict opened or settled meanwhile), so no conflict is settled unseen. Nothing is the suggested action and no button is the filled one. Undo is only the top bar's (owner decision, 2026-10-27), which names it "Undo (conflict resolved)" or "Undo (conflicts resolved)". A crate membership (field `playlist:...`, values in and out; 1.10 "Crate membership") is named by its crate, "In ‹crate›" with the names of its folders before it (`ConflictField.crateName`, `conflicts::membership::crate_labels`; a crate the app no longer has is named by the last name of its key), never by its field name, and its values read "In crate" and "Not in crate" (1cB-20). A pane is labelled by an id of its own, not made of the field's name, so a playlist name with a space, a quote or an accent works. The commands are `review_conflict_fields`, `review_conflicts` (paged), `review_resolve_conflict` and `review_resolve_conflicts`.
- **Analysis fields never conflict**, because the app doesn't edit them. The database enforces it (1aE-11). Conflicts are about tags, genre, comments, rating, color and playlist membership.
- **This is mandatory.** A rekordbox "Yes" is a full overwrite (§5.2), so any rekordbox-side edit not merged before sending is destroyed.
- **Second channel** (owner decision, 2026-10-28; built in 1cB-4, 2026-10-28): a file tag is never taken as rekordbox's value. rekordbox writes a DJ's edits into the file (§5.1), so a track rekordbox has whose file changed after the export a send is built from may carry an edit made in rekordbox since that export, which the send would overwrite. The send review counts those tracks, lists them on request ("Show tracks") and asks to export the collection again from rekordbox. It is a warning: it needs no confirm, the send still goes if the DJ chooses, and the send's token doesn't cover it, so it never refuses the go. **The sign** (`send::preflight`, `changed_after_export` and `changed_on_disk`): the file's modified time is later than the export's own modified time, to the millisecond, either as the last scan recorded it (`file.mtime`) or on disk now, looked up once by the prepare step after its database job (fix round 1 of PR 127: the scan alone missed the main case, an edit in rekordbox and a send straight after, since Watch for changes is off by default). The file is the one rekordbox's entry is matched to (a trusted match), since rekordbox writes into that one; the track's linked file only when the entry has none. A file whose drive isn't connected or is a network drive, or that can't be looked up, keeps the scan's answer. Both times are the file system's (a FAT or exFAT drive keeps times to 2 seconds or 10 ms, so a write within that of the export can count either way), and the app never writes an audio file in Phase 1, so nothing it does sets the sign off; rekordbox does when it analyzes a file after the export (it sets a new modified time), and so does any other program that changes the file. Only tracks sent with the export's values count: a new track's values come from its own file, and a track the send leaves out overwrites nothing. A comparison of tags wasn't chosen: the app keeps no earlier copy of a file's tags (it would need a new table), and the modified time catches every rewrite the tags would. Cost: two reads of the database, then one listing per folder holding 8 or more of the files (it gives each file's modified time without opening it, as the scan's walk does) and a lookup for each other file. Measured in a debug build (2026-10-28): 1.5 s on disk for 100,000 files in one folder, within a prepare of 100,000 tracks rekordbox has that takes 201 s in all. The go never looks again, and the token doesn't cover the list. No migration.
- **How the engine applies it** (`conflicts`, 1cA-1 and 1cA-2, 2026-10-12; merged before every send since 1cB-3, 2026-10-28; the screen is built, 1cB-1 and 1cB-2 above):
  - **The three sides are inputs.** rekordbox's value is its entry's attribute in the newest read, the base is `sync_base`, and the app's is whatever the app means to change (1.9 rule 1). The app's own values are kept per field in `app_value` (§2; 1cB-18): the user's edit and the rekordbox value it replaced. A field the app holds no value of its own for takes rekordbox's. No screen edits a field yet; the only values of the app's own today are the ones settled conflicts store (below) and the ones a merge of two Library tracks gives the track that stays (1.12; 1cB-20).
  - **Both changed to the same value isn't a conflict.**
  - **A field is compared by its kind, never as plain text:** `Location` by its decoded key (1.9); `Rating` by stars, no rating being 0 stars; `Colour` by the color; dates and numbers by value (for `DiscNumber`, `TrackNumber` and `Year`, 0 is rekordbox's "none"; a `PlayCount` of 0 is a real count); everything else as text in NFC, where all-blank text is no value and **a difference in letter case or spacing is a change** (default, the owner may overrule). A value that doesn't parse as its kind is only equal to the same text. `Comments` is one field, My Tags block included.
  - **A field that was never sent has no base.** If the two sides hold the same value, nothing happens. If they differ, it's a conflict recorded without a base: nothing proves either side unchanged. The exception is when rekordbox still shows the very value the app's edit replaced (below): then only the app changed, and its value is sent.
  - **A send that was never imported isn't "rekordbox changed it back".** After a send the base is the app's value, and if the XML was never imported (or the dialog answered No) rekordbox still shows the old one, which by the rule above would be pulled in over the app's edit. When the value the app's edit replaced is known and rekordbox still shows it, the app's value stands and is sent again; nothing is taken in and no conflict is recorded (foreman default, 2026-10-12; the owner may make it a conflict instead: one constant, `NOT_TAKEN_UP`). For a field never sent, the value the app's edit replaced is the one the edit store recorded with the edit (1cB-18). For a field sent before, it's the one the send recorded with the base: what rekordbox's entry at the `Location` sent showed in the newest read when the send was recorded, kept only when the base differs from it by the field's kind (`sync_base.replaced`, §2; 1cB-19). Once a read shows the send taken up (rekordbox's entry there, a row of that read, holds the base of any field the send changed), every record of that send for the track is forgotten in the read's own transaction, since an import overwrites a whole entry; so a later change back in rekordbox is rekordbox's, taken in or a conflict by the rules above, never sent over again. A row kept from an older read, or a `Location` with two rows in the read, forgets nothing.
  - **A rekordbox row kept from an older, incomplete read decides nothing** (§5.3): no conflict is opened, updated or withdrawn from it. A track with no trusted rekordbox entry has nothing to merge, and **its open conflicts stay as they are** until the user resolves them or removes the Library track (they may hold the only copy of rekordbox's value); if its entry comes back in a later read, the same conflicts are decided again by these rules.
  - **Detecting isn't an operation.** It's derived from the three sides, so it isn't in the operation log and Undo never takes a detected conflict away. A rerun on unchanged sides writes nothing. An open conflict is updated in place when a side changes again, and withdrawn (deleted) when the sides no longer disagree: it only held copies of values that live on their sides.
  - **A settled conflict is never changed by detecting.** It's the user's decision and the only record of the value that lost. It stands while rekordbox's value and the base are the ones it was settled on and the app's value is the one it was settled on or the one chosen: the value chosen is what goes out, **whatever the comparison says** (a value given by hand that is the one last sent would otherwise read as "only rekordbox changed" once the app holds it, and the value the user turned down would come in). Once a side moves, the rules above apply again; if that's a conflict, it's a new one, and the settled one stays. Of a field's settled conflicts only the one settled last answers, by its id, not by the clock.
  - **Resolving** (keep the app's, keep rekordbox's, or a value given by hand, which must be a value of the field's kind; in bulk by field, by tracks, or both) is one operation per call, so one Undo takes back a whole bulk resolve and the conflicts are open again with all three values. A settled conflict is a new row replacing the open one (the table's checks tie status, time and value together, and the log writes one field at a time). Undo is refused if the field has a newer open conflict, and once a send carried the field since (that send moved the base to the value chosen, so the conflict put back would read as "only the app changed"; 1cB-3). **The app's own value takes the decision** in the same operation (1cB-3): keeping rekordbox's value clears it, keeping the app's or a value given by hand sets it (an edit already stored keeps the value it replaced; a new one records rekordbox's value in the conflict). So once the decision stops answering (a send moved the base), the value turned down never goes out again.
  - **Merged before every send** (1.9 rule 2; `conflicts::merge`, 1cB-3, 2026-10-28). The send's review runs detection on every Library track's three sides first, in its own writer job, and the go runs it again before it rebuilds the send: on sides that haven't moved it writes nothing and chooses the same values, so the file is the one reviewed. Per field: **only the app changed** (or a send not taken up, or a track rekordbox has no trusted entry for) → the app's value is sent and becomes the base; **only rekordbox changed** → rekordbox's value is sent and the app's own value is deleted, outside the operation log like the rest of detecting (it's derived from the three sides), so the app holds nothing of its own for the field any more and Undo of the edit is refused afterwards as "changed since"; **a settled conflict that stands** → the value chosen is sent; every other field, analysis fields included, goes as rekordbox wrote it. A value chosen that is the one rekordbox already has, by the field's kind, leaves rekordbox's text as it is, and a value that is no value for its kind adds no attribute. `TrackID`, `Location` and the analysis fields are never the merge's to choose. A row kept from an older read decides nothing (such a send is refused anyway).
  - **A field with an open conflict at send time** (owner decision, 2026-10-28; `conflicts::open_at_send` is the one place that says it): the send still goes, carrying rekordbox's current value for the field (the file's, for a track rekordbox doesn't have), so a Yes in rekordbox destroys nothing; and the field keeps its base (or stays without one, whether or not rekordbox's entry has the attribute), so the conflict is still open after the next read and the app's value waits in Review → Conflicts, rather than reading as "only the app changed" and going out unasked. The review says how many fields of the tracks sent wait there.
  - **Crate membership** (`conflicts::membership`, 1cB-3, 2026-10-28) is merged in the same step, one pair (a crate, a Library track) at a time, by the same rules, with the values in and out. The app's side is whether the crate holds the track; rekordbox's is whether its playlist at the crate's path (names compared as the writer compares siblings) holds the track's own trusted entry in the newest read; the base is whether the last send that wrote that playlist put the track in it (`sent_entry`, §2; 1cB-19). **Only a playlist the app itself sent is compared** (1.9 rule 6), and only while a crate of the app has that path: a playlist the DJ made, even inside `Crates`, a crate renamed, moved or deleted in the app, and a playlist renamed, moved or deleted in rekordbox (or not imported yet) are never compared, and the crate goes out as the app has it. **A track the DJ adds to or removes from the playlist in rekordbox is taken into the crate**: its entry is added or deleted, outside the operation log like any take-in (so an Undo of the crate change it overtook is refused as "changed since"). Only the app changed → the app's membership is written. A send never imported isn't "the DJ changed it back": each send records which tracks it changed in rekordbox's playlist (`sent_playlist.replaced`, §2), forgotten once a read shows that send taken up, as for fields. A row kept from an older read, and an export saved before the last send that wrote the playlist, decide nothing about it. With a base, both sides can't change differently; a pair is a conflict only for a playlist last sent before its entries were recorded (no base), and then it's handled like a field's: rekordbox's membership is sent, the conflict's base doesn't move, and the conflict stays open until settled; settling it adds the track to the crate or takes it out, in the resolve's own operation. Entries of the playlist in rekordbox that no Library track is sent as can't be taken in; the review lists the crate as losing them and the send needs the confirm, whether or not the playlist is compared (a playlist the DJ made with a crate's name is replaced on import too, §5.2). An open membership conflict on a playlist no longer compared (its crate renamed, moved or deleted in the app, or its record forgotten) is withdrawn: unlike a field's, it holds no value that lives nowhere else. A track taken in goes last; the order of a playlist's tracks isn't compared.
- **Complexity:** L.

#### 1.11 Track browser with stages and keyboard · 1c
- **What:** a virtualized table with full-text search, filters, columns and a preview player.
- **Stages:** Overview → Review → All music → Library → Crates; Inbox arrives in Phase 2 and Playlists in Phase 3.
- **Hidden filter** (in All music; 1cB-5; `hidden`, `src/hiddenFiles`): a "Hidden" switch beside the search box replaces the track table with one row per file the app isn't showing, each with its reason in plain words and a way back where one is built. It is read a window of 200 rows at a time (`hidden_files_page`; searched like All music, sorted by Title, Artist or File), never as a whole list. The ways back:
  - "Show again" for files you hid: built (`show_file_again`; one operation, so Undo in the top bar hides the file again exactly as it was). Nothing in the app hides a file yet, so it is tested with a file whose reason a test sets.
  - "Use this file instead" for extra files (1cB-22, owner decision 2026-10-28): built for tracks outside the Library (`use_this_file_instead`; `hidden::choose`). An extra file's row says which file is its track's best, and the button makes that file the one the track shows. It is remembered by what the file holds (`file_choice`, §2), so the ranking respects it from then on: the next ranking run, a rescan, a retag (the choice follows the file's new bytes), a move and a music folder removed and added again don't undo it, and the ranking gives the reason "you chose this file" (1.7). It is one operation: Undo in the top bar takes it back exactly and the ranking's own choice returns. If the chosen file is gone from disk, or is encoded again (other audio), the ranking decides again; the choice stays and holds again if the file comes back. A button is offered only for an extra file that is on disk, has a hash, isn't hidden for another reason and isn't the very same bytes as the file shown (nothing could tell the two apart). **A Library track's extra file has its reason and no button** (switching would make it a new rekordbox entry whose cues stay behind; revisited with 2.6), and the backend refuses it too. **Once a track is in the Library its choice has no say at all**: the ranking, and Review's rules that read it ("Linked file gone, copy found", "Better file available"), work as if there were none; the row stays and applies again if the track leaves the Library.
  - "Put back in Inbox" for cleared Inbox files (Phase 2: such a file is listed with its reason and no button).
  - **One rule for what All music shows** (1cB-5): a track is in All music when it has a file with no `hidden_reason`, an extra copy included. The Overview's All music count, the track table's All music rows and count, and "N hidden files match" all read that one rule (`hidden::has_shown_file!`), applied when a query runs, so hiding a file, showing it again or undoing either changes the lists at once. A Library track whose files are all hidden stays in the Library.
- **What search covers** (owner decision, 2026-10-12; index 1cA-6): title, artist, album, remixer, label, genre, comment and file name. Capitals and accents don't matter, and a word matches from its start ("hou" finds "House"). Results keep the list's own order; there is no relevance ranking. "N hidden files match" counts only hidden files whose track isn't already in the results, that is, whose track has no file without a `hidden_reason` (owner decisions, 2026-10-12; 1cB-6).
- **Search finds hidden files too** (1cB-6; `hidden_files_matching` over `search::find`, `HiddenMatches`): under the search box in All music, "N hidden files match · Show them" appears when the search matches hidden files whose track isn't in the results; "Show them" opens the Hidden filter with the same search. The Library has no search box yet, so the line is not shown there.
- **The track table** (1cA-3, 1cA-4; owner decisions, 2026-10-26; `track_table`, `src/trackTable`): one table for the Library, All music and a crate. Descending is the ascending order read backwards (blanks still last), so tracks that tie come in the reverse of the order they have going up: for example artists that tie by title Z to A, then the later track first. A crate keeps the order its tracks were added until a heading is clicked. Not shown yet, for want of data: Album, Year, Energy, Comment, Label, Play count and the rest of the columns a DJ library has; the list of columns is data, so the column editor (1cA-5) only hands the table another list. **The column editor** (1cA-5, owner decisions of 2026-10-26; `ColumnEditor`): a "Columns" button above the table opens a panel to show, hide and reorder the columns with buttons (move up, move down, hide, show, so the keyboard reaches all of it) and "Reset to default" (the first columns, order and widths); Title can't be hidden. Widths are remembered per screen with the column choices, in the same `ui_setting` value, and "Reset to default" clears them too; a column without a width keeps the Designer's default. A click on a heading still sorts, and the click that ends a drag does not. The table is redrawn once per animation frame while a width is dragged, without redrawing its rows, and the choice is saved when the drag ends. It is no Library data: it is not in the operation log, can't be undone and is kept by "Start fresh". An id that is no longer a column is ignored, and a column added by a later version appears hidden unless it is a default column of that screen. **Sorting keeps the selection** (owner decision, 2026-10-26): when the list is sorted or reversed, the focused track stays selected and the table scrolls to it (of a selection of several, only that track: the others are let go); with nothing selected the list starts at the top. A filter or a search keeps it too while the track is still listed (`track_table_position` counts the rows before the track with the very SQL of the window, so the two can't disagree). Above the table are the **filter chips**, each with an × to take it off: Missing, In rekordbox, Not in rekordbox, Format (any of the formats chosen) and Quality problem (exactly what Review's "Quality problems" group holds, 1.12, by the same SQL text, worked out when the query runs: a Library track whose linked file is flagged, cut off or broken with no better copy and no "Keep anyway" or "Find a better file" answer, or a "Better file available" item whose linked file is still there) on all three screens, In a crate and In no crate in the Library, In Library and Not in Library in All music. A filter and its opposite replace each other, and the filters work together with the search. Free filters such as "BPM 120–126" are 1cB's. What the order and the filters read is `track_row` (§2), which the index job writes in the same step as the search index, except that All music also leaves out a track whose files are all hidden, worked out when the query runs ("One rule for what All music shows", above); what a row shows is worked out again for the rows on screen, so a row is never stale, only possibly out of place for the moment the index job takes to catch up.
- **The Details panel** (1cB-17; `DetailsPanel`, `TrackDetails`, `track_tag_sources`): beside the Library, All music and a crate, it shows the selected track. At the top are its **full title and the full path of its file**, wrapped, never cut off and plain text to select and copy (the answer to the cut-off cells' hover text, `docs/design-style.md`). Under them is **each tag field with its value and where it comes from**: Title, Artist, Album, Genre, Composer, Remixer, Label, Year and Comment, those that have a value. For a Library track rekordbox knows, the value is rekordbox's; a field rekordbox leaves blank has no value (a file's tag doesn't stand in for it, 1.13). For any other track it is the tag of the file the track shows: the linked file for a Library track, else the best file. The other values the track's sources hold for the field are counted beside it, and listed, each naming its file, when **"More details"** is on (the same switch as Review's comparison, off at first): a file's tag that differs from rekordbox's (the linked file's first, then the track's other files on disk, best first), or, where there is no rekordbox value, the other files' values that differ from the one shown. A file that agrees isn't listed. The rules are the lists' and the send's own (`send_values::sources`, over `Loaded::source` and `Loaded::tag_order`), so the panel can't say something else than the track shows. For a Library track whose rekordbox entry was **confirmed** to its linked file (a trusted match with a `relink` row of the Location), a quiet text button, **"Withdraw confirmation"**, withdraws it (`review_withdraw_relink`, 1.12): one undoable operation, with Undo in the top bar only, and the entry is decided again from scratch. **Crates** (1cB-14; `TrackCrates`, `crates_of_track`): for a Library track, the crates it is in, in the order of the tree, each a link to the crate named by its place ("Friday residency › Warmup") with "Remove from this crate" as a plain text action beside it (one undoable operation, `remove_tracks_from_crate`; Undo in the top bar only); "In no crate" when there are none. A track outside the Library is in no crate and shows nothing here.
- **Keyboard** (1cB-7 palette, below; 1cB-8 the rest; `TrackTable`, `useTrackKeys`): **Selecting many tracks.** A click selects one row; Shift+click selects the rows from the last click to this one; Ctrl+click adds a row or takes one out; Ctrl+A selects every track in the list, those not on screen too (`track_table_ids` gives the ids of a range of the query's rows, the window's own SQL, up to a million at once); Escape selects none. Only selected rows are tinted; the focused row of a selection of several (or of none) has a ring instead, and a line over the table says how many are selected (from two). Sorting, filtering or searching keeps only the focused track selected. **J and K** move the focus down and up and select that row alone (from the top of the screen when no row has the focus); Shift+J and Shift+K extend the selection from where the last click or move started, and the arrow keys with Shift do the same. **1 to 0** give every selected track an energy of 1 to 9 (0 is 10) as one operation, so one Undo, in the top bar, takes them all back (§2, `analysis`); nothing is sent to rekordbox, and no screen shows energy yet. A line over the table says what the key did (the energy and how many tracks) until the focus moves, the selection changes or something is undone. **Space** plays or pauses the preview player, and is available while a file is loaded in it (the full player arrives with 1cB-10); a button or link that has the focus keeps its Space. **C** opens "Add to crate or playlist" for the selected tracks (1.14, "Adding"), and is unavailable with none selected. **T** (tag) is registered and unavailable until tags exist (3.1). The keys never fire while the focus is in a text field, while a dialog is open (the palette is one), or for a key another handler already used; a held J or K keeps moving, while the other keys act once. Every key is an action in the palette's registry, listed with its shortcut.
- **Command palette** (1cB-7; `src/palette`): Ctrl+K opens a dialog with a text box and a list of actions, from anywhere and from inside a text field, but not over a question waiting for an answer. Typing filters the list: every word typed must start a word of an action's name (capitals and accents don't matter); the list keeps its order, with no ranking. The arrow keys (and Home and End) move the highlight, Enter runs it, and Escape or a click outside closes the palette and gives the focus back to where it was; the focus stays in the box while it is open. An action that can't run now isn't listed, and one with a keyboard shortcut shows it. **One registry of actions** (`registry.ts`) is all the palette reads: whatever owns a handler registers its action (`useRegisterActions`), so the palette runs the very handler the screen's own control runs and has no behavior of its own. The track table's hotkeys (1cB-8, above) register into the same list as source `tracks`, between the app's actions and Undo; an action that can't run now (Clear selection and the energy keys with no track selected, Space with no file loaded, T for now) isn't listed. Listed today: Go to each screen (the five stages and After import), Search All music (opens All music with the cursor in its search box; the Library has no search box yet), Send to rekordbox (opens the guided send on the Overview and sends nothing; listed once the Library has tracks), Undo (the top bar's own handler, with Ctrl Z) and Theme (the one not in use). While it is open the other shortcuts don't fire: it is a `dialog`, which they already stand aside for.
- **Audio:** preview in the webview over a custom Tauri protocol, with AIFF and ALAC decoded to PCM/WAV in Rust. The page's content security policy allows that one local protocol as a media source and nothing else new; it serves only files the app has scanned, looked up by id, with no network (owner decision, 2026-10-13: a security setting, and the test that keeps the policy strict is changed on purpose for it). Waveforms are computed once in the job queue and cached as peak arrays (1cB-9): the `waveform` job decodes each file once, at the lowest priority and one file at a time, after the hashes and the fingerprints and wherever quality is asked for, and keeps at most 1024 buckets of a peak and a level byte (at most 2 KiB a track) in `file_waveform` (§2), keyed by `audio_hash`, so a retag costs nothing, changed audio is drawn again and files that hold the very same audio share one waveform (copied, not decoded again). It stays behind everything else: between files it gives its thread back and waits while any job of a higher priority runs, and stops for one that is queued. The file the player has loaded is drawn first (`waveform_first`: a job for that file alone, at user priority, that waits for nobody). The `waveform_peaks` command answers from the database for a file id (the file a track shows): the peaks, "not ready" while the job hasn't reached the file, or "unavailable" for a file that can't be decoded; it never decodes. The player bar draws them with a playhead (`src/player/Waveform`), a placeholder until then.

#### 1.12 Review screen · 1b
- **What:** every decision the app can't make alone. Phase 1 covers duplicates, possible version mix-ups, quality problems, relink confirmations and "Better file available", with conflicts (1.10) in 1c. Later phases add tag suggestions (2.2) and unmapped genres (3.2).
- **Scope:** Library tracks, plus every relink match waiting to be confirmed, in the Library or not: a track whose only rekordbox match is probable can't be added until it is confirmed (1.8). Adding is instant, so there is no "being added" state (owner decision, 2026-10-12). Duplicates among tracks you never add aren't queued, though All music still shows them. The Missing list (1.3) stays its own section below the queue and isn't counted in "how many need a decision". Inside a group the oldest item comes first.
- **Layout:** a queue on the left and a comparison on the right. The queue is grouped by how much thought each item needs: "Needs a closer look" first, then "Clearly best file", then "Quality problems", then "Conflicts" (1cB-1, 1cB-2). It shows how many are left.
- **What each group holds in Phase 1** (owner decision, 2026-10-12):
  - "Needs a closer look": possible version mix-ups (pairs the rules send to review), duplicate sets held because their pairs disagree, two Library tracks that are the same recording (1.4), and relink matches to confirm (1.2).
    - An "Unclear duplicates" item's reason says what holds the set, naming files that the table always shows, by the names it shows. It tries, in this order: two Library tracks in the set; two files whose pair the rules did not call duplicates, with that pair's first two reasons in the words a possible version mix-up uses (one such pair holds the whole set, even when the other files hold the very same audio); two tracks the user kept separate; two tracks linked as versions; and more than 50 files that hold more than one kind of audio. When none of these shows in what is stored, it keeps the old reason, a duplicate pair's own (1bF-3, 2026-10-24; `review::held::holding`).
  - "Clearly best file": a Library track whose linked file is gone while another copy of the track is on disk. Switching to that copy is the only choice "Accept all N" makes.
  - "Quality problems": a Library track whose linked file is flagged, cut off or broken, with no better copy; and "Better file available" items whose linked file is still there (so a flagged track that has a better copy is here too, as a better-file item).
  - "Conflicts" (1cB-1, 1cB-2, 2026-10-28; see 1.10 "Conflicts queue"): one line per field that has open conflicts, with how many, in the order of the names the user sees. A conflict is not a Review item (it has no files and no suggestion), so the group selects a field, not an item, and the field's conflicts take the place of the comparison. Like every group it is left out while it has nothing, and "No items to review" shows only when no group has anything. Up, Down, Home and End move through the fields as they do in the other groups. **Enter, S and the number keys do nothing on a conflict:** there is no suggested action, so nothing is decided by a key, and each conflict is settled with its buttons. Each open conflict counts once in "how many need a decision" (`review_counts`: `conflicts`, and in `total`, so the Overview and the sidebar include them; foreman's ruling, 2026-10-28), and the empty state shows only when that total is 0.
- **"Better file available" in Phase 1** (owner decision, 2026-10-12): the item shows the better file and its reason (1.7) and can be dismissed; the dismissal is remembered. A dismissal covers that one file: a different, better file is a new item. Switching the linked file is offered only when the linked file is gone. For a track rekordbox knows the item says plainly what the switch means there: the XML can't change a known track's location, so rekordbox sees the copy as a new track without the old entry's cues and the old entry goes on the list to remove in rekordbox; relocating the file inside rekordbox keeps the cues. (That is the case where rekordbox's entry isn't trusted on the copy; the other case is in "How the actions work" below.) "Accept all N" for "Clearly best file" is this same switch. The Upgrade action arrives with managed copies (2.6).
- **"Accept all N"** for clear cases. It can be undone, and what it accepted stays viewable: afterwards a line at the top of Review says how many tracks were switched to the copy on disk, with View (each track with its old and new file) and Undo, and it stays until it is dismissed or the next "Accept all" (owner decision, 2026-10-13).
- **How the actions work** (1bE-5, 1bE-6, 1bE-7, 2026-10-13; 1bE-9, 1bE-2, 2026-10-16; `review::actions`, `review::same`, `review::split`). Each is one operation in the log, so Undo takes it back and the item is in the queue again; the queue is right as the action or the undo returns, without waiting for a background job (for up to 500 tracks in one step; beyond that when the roles job ends).
  - **Remembered by what the files hold** (`review_decision`, §2): a dismissal, "Keep anyway" and "Find a better file" name the audio the track is linked to (and a dismissal the better file's audio too), never a file or track id. They survive a rescan, a retag and a move; a file that is encoded again holds other audio, so it is a new item. A file that hasn't been hashed yet can't be decided about.
  - **Dismiss** is offered on "Better file available" items whose linked file is still there. A "File missing, copy found" item has no "don't switch" (owner decision, 2026-10-13).
  - **A dismissal hides only that one file** (foreman's default, 2026-10-13; the owner is asked). The track is then offered its best-ranked better file that isn't dismissed, a new item, as the dismissal returns; the stored best file and the ranking (1.7) don't change, only which file is offered (`file_roles::offered_better`, the one place that skips dismissed files; a dismissal made or taken back makes the track due for the roles job). When the linked file is flagged and every better copy is dismissed, the track is a single-file "Quality problem" item again ("Keep anyway" / "Find a better file"): dismissing a copy is no decision about the flagged file. A copy that is on disk while the linked file is gone is offered whatever was dismissed.
  - **What a switch means in rekordbox is the send's own answer** (1.9), asked for the track as it is linked now and as it would be linked to the copy; a switch never overrides relink's match (owner decision, 2026-10-13: cues are kept when rekordbox's entry is already matched with trust to the copy; otherwise a new track, and the old entry on the remove list). *rekordbox's entry stays the track's* where relink trusts that entry on the copy, or the user confirmed it there: the track is still sent as that entry, with rekordbox's old `Location`, so rekordbox keeps the track and its cues and shows the file as missing until it is relocated there. *A new track* where the entry is matched to the copy only probably, or to nothing: the track is sent from the copy as a new track without the old cues, and the old entry is recorded (`replaced_entry`, §2) and listed with the tracks to remove in rekordbox (1.9 rule 7), until a read no longer has it or the entry is trusted on the linked file, or on a byte-identical copy of it (1.9), after all. *Another entry* where rekordbox already holds the copy as a track of its own: the Library track is sent as that entry from then on, and the old one is listed to remove. A track rekordbox doesn't know has nothing to say. The item shows which case it is, and the switch works it out again when it is made: if it is another case by then, nothing is switched and the item is shown again.
  - **A switch is refused** when the linked file is on disk after all, when the file to switch to isn't a file of the track, is gone itself, or is linked by another Library track, and when a rekordbox entry matched to that file is the entry another Library track is sent as (that track would lose it, as the automatic follow holds there, 1.8).
  - **Undo of a switch after a send.** A switch that made the track a new one for rekordbox (a track rekordbox didn't know, or one whose entry isn't trusted on the copy) can't be undone once the track has been sent since: the copy's new entry is in rekordbox by then, and taking the switch back would leave it there with nothing to list it. It is refused with its own reason, as undoing the add of a track that was sent since is (the add's rule is stated in §2, `operation` / `change`, and in 1.9, "Rule 8"). A switch that kept the track rekordbox's own entry, or made it another entry rekordbox already held, adds nothing to rekordbox, so it can be undone after a send too. Before any send every switch can be undone (foreman's ruling, 2026-10-13).
  - **After a switch** the track's files are ranked again at once, for the new link. Nothing pulls the link back: the automatic follow only acts while a linked file is gone (1.8), and relink never writes a link (1.2).
  - **"Same track twice in your Library"** (two Library tracks that are the same recording, 1.4; 1bE-9, owner decisions 2026-10-12; `review::same`). The item shows each Library track's cues, rating and plays in rekordbox (of the entry it is sent as; "Not in rekordbox" for a track rekordbox doesn't know) and how many crates hold it, with the files table. Two buttons: *Merge*, the one filled button, which only opens the choice of the track that stays (the suggested one chosen), the values to pick where the tracks differ (below) and the confirmation, "Merge" / "Go back"; and *Keep both*. With three or more Library tracks in the item, the others all merge into the one chosen and "Keep both" keeps them all (owner decision, 2026-10-16). The suggested track to keep is the one with more cues (the track that stays keeps its own cues, the other's are lost), then more plays, then the one holding the best-ranked file, then the older one, with its reason (owner decision, 2026-10-16; one function, `suggest_keep`). Both actions send back the tracks the screen showed and are refused if the item has other tracks by now.
    - *Keep both* remembers "apart" between every two of its Library tracks (`grouping_decision`, §2, by what the files hold): never merged, never asked again. A copy outside the Library in the item then stays a track of its own, and isn't asked about.
    - *Merge* is the explicit, confirmed, undoable action a Library track is deleted through (CLAUDE.md). The track that stays keeps its own cues, grid and play count, and its own BPM and key (owner decision, 2026-10-12; BPM and key: foreman's ruling, 2026-10-16, see `analysis` in §2); cues stay with the entry kept. Its other values are asked field by field (owner decision, 2026-10-28; 1cB-20, `review::merge_fields`): one row per field where the tracks hold different values and at least one is the user's, meaning their edits in the app (`app_value`, §2) and rekordbox's rating, color and comments, My Tags included, of the entry a track is sent as; a row shows each track's value side by side, as the conflicts do (1.10), with the staying track's value chosen at first. A value only one track has, and that is the user's, carries over without asking; a tag read from a file or any other value of rekordbox's is nobody's choice and never makes a row. No value is blank text, no stars, no color, or a 0 where rekordbox writes 0 for none. A value taken from the track that leaves becomes the staying track's own value (`app_value`, with what rekordbox shows for the staying track as what it replaced), in the merge's own operation, so the next send carries it by the rules of 1.10. A value chosen is the user's decision against what rekordbox shows for the staying track now (`app_values::set_chosen`): it records that value as what it replaced, a base (`sync_base`) rekordbox's value has moved off since the send is dropped as if the field were never sent, and an open conflict on the field is withdrawn, all in the merge's operation, so the next send carries the choice as an app change and rekordbox's change since the last send is neither taken back in nor asked about again. The screen asks `review_merge_questions` for the rows, and `review_merge` takes the values picked, each with the text shown: it is refused as the item changed if one is no longer the track's value. For each track that leaves, in one operation: the rekordbox entry it was sent as goes on the list to remove in rekordbox (1.9 rule 7), except while the track that stays is sent as it: a staying track with no entry of its own whose linked file is byte-identical to the leaving track's is sent as that entry (1bE-11; 1.9, "A byte-identical copy's entry"), so rekordbox keeps the track and its cues; a crate that held it holds the track that stays, with the same entry kind, and where a crate held both the staying track's own entry wins; its sync bases, conflicts and Library track are deleted; its files join the track that stays; its track is kept with no files while the merge stands (`track_merge`, §2). A copy outside the Library then joins the merged track. Tracks linked as versions are never merged: such an item offers only "Keep both", with a line saying why, and a merge sent anyway is refused.
    - *What runs as the action returns:* only the logged writes, and a grouping pass over the item's own files (the files of its tracks and every file that could join a set with them), so the item, and a copy outside the Library joining the merged track, are right as the action or its Undo returns; the grouping job does the rest of the library (foreman's ruling, 2026-10-16; about 0.5 s for one merge beside 100,000 files in a debug build, where a whole pass takes about 7 s).
    - *Undo* of either brings everything back, the two tracks, their crates and the values chosen included (both tracks' `app_value`, `sync_base` and conflicts exactly as they were, before a send), and the item is in the queue again. A merge can be undone after a send, as a removal can: it writes nothing a send changes, and the next send sends the track that came back (foreman's ruling, 2026-10-16). **The Undo of a merge is refused**, with its own reason and nothing changed, once the track that stayed is linked to another file than at the merge, or a file the merge moved is a Library track's linked file: it followed its file to one the merge moved (1.8), or was switched. Taking the merge back would then leave two Library tracks on one file (foreman's ruling, 2026-10-16).
    - Keys (owner decision, 2026-10-16): Enter and S do nothing on this item, and a number key picks which track stays: it opens the merge's confirmation with the track of that row chosen (see "Keyboard").
  - **A possible version mix-up and "Unclear duplicates"** (1bE-2, foreman's answers 2026-10-16; `review::split`). Two buttons: *Same track*, and *Not the same* on an item with two files or *Split off* on one with three or more (S). The filled button follows the evidence (owner decision, 2026-10-24): on a possible version mix-up whose own reason says the names give different cuts or reworks (`namesSayCut`, `namesSayRework`), *Not the same* is filled on an item with two files; with three or more no button is filled until a row is selected, then *Split off* is. Everywhere else *Same track* is filled. Enter always does the filled button, and nothing while none is. A file row is selected by a click, or Space while it has the focus; none is selected at first, and *Split off* is greyed out, and the keys line says to select a row, until one is. Each is one operation; Undo takes it back exactly and the item is open again. A refusal shows its reason under the buttons at once.
    - *Same track* remembers "same" between every two of the item's tracks (`grouping_decision`) and moves the files of the tracks outside the Library into the Library track; each track that lost its files is kept, with none, while the decision stands (`track_merge`, kind `same`), so Undo can move them back. The job's own version links between them go; a link the user made or confirmed refuses it (versions never merge). It never merges two Library tracks: with two in the item it only remembers "same", and the pair is then "Same track twice in your Library", with its own Merge.
    - *Not the same* remembers "apart" between the two files' tracks; nothing moves. Two files that share a track are split instead (the file split off becomes a track of its own): the selected row, else the file that isn't the suggestion; the Library track's linked file never leaves (foreman's ruling, 2026-10-16; on the two kinds S works on today an item always has two tracks or more).
    - *Split off* makes the selected file a track of its own for good (owner decisions, 2026-10-12), together with every file of the item that holds the very same audio (an equal `audio_hash`; owner decision, 2026-10-24): they move into a new track together, and "apart" is remembered between it and every other track of the item, the one they left included, so the grouping never merges them back and relink no longer matches them with the files they left. When the copies already make up a track of their own, they stay in it and any copy elsewhere joins them. The linked file of a Library track can't be split off: when it or a copy of it is selected, the copies join its track and its other files leave instead, together as one new track, apart from the linked file's track. A split is refused, with its reason, when the selected file and its copies are every file of the item, when two tracks hold nothing but copies, or when the copies are the linked files of two Library tracks (a reason of its own). After a split that leaves the item's other question open, the screen stays on the item; otherwise the next item loads.
    - Undo is refused, with nothing changed, as "changed since" when a track a split took files out of may be another track by now, or when a file the action moved isn't that file any more or is a Library track's file now (§2, `operation` / `change`).
  - **A "rekordbox match uncertain" item** has two buttons, "Confirm" and "Not the same" (1.2). Both answers are kept by the audio the file holds, so they outlive a move or a rename of the file and its music folder removed and added again, and removing a music folder is never refused because of them (foreman's ruling, 2026-10-14). "Not the same" waits until the file has been hashed. A match the user confirmed before, whose file holds other audio now, is the same item with "Confirm again", and says why it is back. A confirmation is withdrawn in the Details panel, not here (1cB-17; 1.11).
  - **"Accept all N" makes the switch only for the clear cases:** a track rekordbox doesn't know, and a track whose entry stays its own. A switch that arrives in rekordbox as another track than today (a new track without the old cues, or another entry) stays in the queue for a decision of its own: "Accept all" leaves out the switches that lose cues (owner decision, 2026-10-13; the rule is one function, `accept_all_covers`). N counts only what it will switch, and a click sends exactly the items the button counted: each is switched only if it is still that item, with the copy it showed, and still a clear case; an item that joined the queue since is never switched unseen (foreman's ruling, 2026-10-13). It is one operation, so one Undo restores every link, and it returns each switched track with its old and new file and each item it left with a reason code; the view of what it accepted (above) is built (1bE-3, 2026-10-16): the line sits at the top of Review whatever the queue holds, it is kept for the session, not only while Review is open, and `review_switched_view` gives the names the switch's ids stand for (the track, the old and the new file). The line has no Undo of its own (owner decision, 2026-10-27: Undo is in the top bar, and Ctrl+Z, only); it goes once that operation is undone from the top bar or with Ctrl+Z, and an Undo of some other step, a failed one or a refused one leaves it.
- **Comparison:** one row per file with the same columns, the suggestion first, and a plain-language reason. "More details" is a switch above the table, off at first and kept on from item to item while Review is open; it adds bitrate, sample rate and date added (the day the app first saw the file; rekordbox's entry has none). The Details panel shows each tag's value for the Library track and which file it comes from; that part is built (1cB-17, owner decision 2026-10-12; 1.11, "The Details panel").
- **Keyboard:** Enter keeps the suggestion, number keys pick another file, S splits the group ("these aren't the same"). The next item loads automatically. In detail (owner decisions, 2026-10-13): Enter only ever does the item's suggested action, its filled button, so a habit of pressing it never hides anything: "these are the same track" on a possible version mix-up and on "Unclear duplicates", except on a mix-up whose names say different versions, where it is "not the same" or the split of the selected row (owner decision, 2026-10-24; see "How the actions work"), the switch to the suggested copy on "File missing, copy found", confirming on a relink match; on a quality problem, on "Better file available" and on "Same track twice in your Library" (a merge needs its confirmation; owner decision, 2026-10-16) it does nothing, and those keep their own buttons. Number keys pick by row (1 is the first row, up to 9) and act only where there is a choice of file today: "File missing, copy found" with more than one copy, where the digit switches to that copy; on "Same track twice in your Library" the digit picks the track that stays, and S does nothing there (owner decision, 2026-10-16). S on an item with two files says they aren't the same; with three or more it splits off the selected row with its identical copies, and does nothing while no row is selected. After a decision the next item in the same group loads, then the first item of the next group that has any, then the empty state once nothing is left (in detail below); after an action the app refuses, the screen stays where it is. The number keys rate energy in the Library (1.11) and pick a file here. **Built** (1bE-2, 2026-10-16): Enter confirms a relink match, switches to the suggested copy on "File missing, copy found", and does the filled button on a possible version mix-up and on "Unclear duplicates": "Same track", or "Not the same" or Split off where the names say different versions (1bF-2, 2026-10-24; see "How the actions work"), and does nothing on anything else; S works on those two kinds only for now (the owner is asked about "Clearly best file"; one place, `review::split::decides_tracks`); a number key switches to the copy in that row when the item has two or more copies on disk (the comparison carries the switch to each copy with its own effect, `copies`), and does nothing on the linked file's row, on a row with no copy or a refused switch, or on any other kind. On "Same track twice in your Library" (1bE-9, 2026-10-16) Enter does nothing, and a number key is a row of the item's table of Library tracks: it opens the merge's confirmation with that track chosen as the one that stays (nothing is merged until "Merge" there); not on an item whose tracks are linked versions. The `.keys` line in the action row says which keys work on the item. The keys are read on the whole screen but never from a focused button, field, link or slider (the play buttons sit in every file row), with a modifier, while a dialog is open or when held down, and an action is never started twice. After a decision, by key or click, the next item in the same group, else the first item of the next group is selected; with nothing after it the selection wraps to the first item left, and the empty state shows only when nothing is left (foreman's ruling, 2026-10-16); after a refusal nothing moves.
- **Listening:** switching between files keeps the playback position. The preview engine (1.11, tasks 1cA-7 and 1cA-8) is built in 1b for this (owner decision, 2026-10-12). How it behaves (owner decisions, 2026-10-13): the position carries by time (1:30 stays 1:30; a file shorter than the position starts from its beginning); a file that was playing keeps playing and a paused one stays paused; there is one player for the whole app, with play/pause and a scrub bar, one file audible at a time, and no volume control or loudness matching in this version. A file that can't be played (missing, its drive not plugged in, not decodable) gets a short line in the player saying which, and no playback. An online-only OneDrive file is never downloaded to preview it: the player says it is online-only.
- **Single-file quality problems:** "Keep anyway", or "Find a better file" (→ wishlist, 2.3). In Phase 1 (owner decision, 2026-10-12) "Find a better file" stores a remembered mark that you want the track in better quality, which the wishlist picks up in Phase 2; either choice takes the item out of the queue for good. After "Keep anyway" the ranking (1.7) still treats the file as flagged: its audio hasn't changed. "For good" is for the audio that was flagged: linked to other audio later (the file encoded again), a flagged track is asked about again.
- **Complexity:** M.

#### 1.13 Overview · 1c
- **Header** (1cB-11, 1cB-12): the four numbers (below) and one main button, "Send to rekordbox". It opens the send review (1.9) and never sends by itself. It carries no count of changes and no "send due" line (decided in 1cB-12): what a send carries depends on rekordbox's export (a known track goes only inside a crate that is sent, a new one always, and each field is compared with the export's), so a count is right only once the review has read the export, and no signal the app keeps by itself is exact (a log of edits since the last send would count an edit undone by hand, a track rekordbox already has, and an edit of a track in no crate). It is greyed out, with the reason beside it, only when the Library can't be read, and the command palette's Send is unavailable under the same rule. When the last read of an export found nothing to send, or refused the send, the header says so, with when the export was read on a line of its own, and the button stays, because the next read may find otherwise. Once the Library has changed since that read (its tracks, or its crates and their counts), the header stops saying it: it described a Library that has gone.
- **What to do next** (1cB-11): one line per thing waiting, each naming it with its count and opening where it is handled; a line with nothing waiting isn't drawn. The Review groups that have items (Needs a closer look, Clearly best file, Quality problems, Conflicts) open Review. Tracks made from low-quality files, tracks with missing tags, tracks with missing art, tracks rekordbox hasn't analyzed (only once rekordbox has been read) and tracks in no crate open the Library, until "Every number is a door" (1cC-4) opens it filtered. Tracks outside the Library (1cB-12: the tracks in All music that aren't Library tracks) open All music. Unsent changes are not a line yet (see Header). A line whose number is still being counted says so, and until every number is in and none is being counted the list says "Still counting", never "Nothing to fix". The empty list says "Nothing to fix". One progress line sits under it ("This week: 4 tracks added, 12 decisions made", "This week: no tracks added, no decisions made" when there are none), with the numbers the Overview command counts.
- **Four numbers** (1cB-12, in the header, right-aligned with tabular figures): tracks and total length (an hour or more as hours and minutes; no length is shown when none is known); how many are in crates or playlists (crates only until playlists arrive); how many rekordbox has analyzed (a dash with the reason until rekordbox has been read once); the date the Library was last sent ("Not sent yet" when never). A number background work can still change says "(still counting)".
- **Charts** (1cB-12): energy spread and genres as one-color bar charts, each bar with its label and its count written beside it and the bars of a chart sharing one scale. Energy: a bar for each energy 1 to 10 and one for "No energy", counting Library tracks by the energy they show (user, then MIK, then local, then audio model; §2 `analysis`); when no track has an energy it says so instead of drawing empty bars. Genres: the 8 biggest, then "Other" (the rest added up, made only when it adds up two genres or more) and "No genre"; when no track has a genre it says so. The color is a theme token (the muted text color: the accent means "selected" and nothing else).
- **What the numbers mean** (owner decision, 2026-10-12): a track's genre is rekordbox's for a track rekordbox knows, otherwise the file's tag. "Analyzed" means rekordbox supplied a BPM or a key. "Decisions made" counts the operations in the undo log; one that was undone doesn't count. "This week" is the last 7 days. A track rekordbox knows with a blank genre there has no genre (the file's tag isn't used instead). "Missing tags" is a Library track with no title, no artist or no genre; for a track rekordbox doesn't know, a title that is only the file name counts as no title (for a track rekordbox knows, its Name there is the title); "missing art" is one whose linked file has no embedded cover; they are two numbers. "Not analyzed" isn't shown until rekordbox has been read once. "In crates" counts the app's crates; playlists join when the app has them. Energy is the one the `recording_display` view shows (§2); the user's own energy (an `analysis` row of source `user`, 1cC-2 and the energy action) wins over the other sources, and a track with none counts as "No energy". "Outside your Library" counts the tracks that All music lists and that aren't Library tracks. A count of unsent changes needs rekordbox's export (see Header), so the Send button and the to-do list carry none.
- **Outside your Library** (1cB-12): one strip with the count of tracks in All music that aren't in the Library, how many items in Review wait for a decision, and links to Review, All music and Manage folders (which takes the user down to the music folders panel on the same screen). The same count is a line in "What to do next", opening All music. Quiet links: Send stays the Overview's one filled button, and "Read newer export" is a filled button only while the Library has no tracks.
- **Every number is a door:** clicking opens the Library filtered, with a visible filter chip saying why.
- **No health score.**
- **Launch:** the app reopens where you left off, except on first run or when a scan or read finds something new; then it opens on Overview. During scans, numbers say "still counting".

#### 1.14 Crates · 1c
- **What:** hand-made crates of Library tracks, built for finding what fits next.
- **Adding** (1cB-13; `AddToCrateDialog`, `useTrackDrag`, `add_recordings_to_crate`): drag the selected tracks onto a crate in the sidebar (a row that isn't selected is selected first and is the one carried; Escape gives the drag up), or press C, or use "Add to crate or playlist" in the palette. The crate under the pointer is outlined in the accent; a folder shows no cue and a drop on it adds nothing and says why, and a stage takes no drop. The dialog is a text box over the crates, each named by its place; typing finds them as the palette finds actions, Enter adds to the highlighted one, and a last row makes a new crate at the top of the tree from the typed name (shown unless a crate at the top already has that name; a folder's name is refused as the sibling-name rules say, and nothing is made or added). Adding is one undoable operation for all the tracks (making a new crate first is another). A track already in the crate is not added twice. **Only Library tracks join a crate:** a track outside the Library is left out and counted ("N not in your Library"); adding it to the Library and the crate in one step is coming in 1cB-23. A line over the track table says how many were added and how many were already there or left out.
- **Folders:** crates live in folders ("Friday residency › Warmup, Peak time") that carry over to rekordbox unchanged. The crate header shows the rekordbox path ("Crates › Friday residency › Warmup").
- **Notes and summary:** an optional notes line per crate, plus a summary line on every crate and playlist: BPM range, energy range, keys, top genres.
- **"Sort by fit after the selected track":** key compatibility (same key or Camelot neighbors) plus BPM closeness. The Fit column shows dots **with the reason** ("8A → 9A, +1.5 BPM"). Clicking a column header returns to normal sorting.
- **Membership** (1cB-14): the Details panel lists a track's crates, each a link, with "Remove from this crate" (undoable; 1.11, "The Details panel").
- **Tags vs crates:** tags (3.1) describe what a track is; crates collect tracks for a purpose. Smart crates (3.3) connect the two.
- **Basics since 1aG (2026-10-02):** a plain Crates screen and "Add to crate" on the Library screen make static crates, rename and delete them, and add or remove Library tracks, each change an undoable operation. A name is trimmed and refused if empty, if the writer can't carry it, or if it equals another crate's or folder's in the same folder as the XML writer compares siblings (1.9), so a crate the app lets you make never refuses a send.
- **Folders as built since 1cA (2026-10-26):** a folder holds crates and folders, never tracks, and the tree can be as deep as the writer allows (63 levels of folders, since a send counts the `Crates` folder as the first of 64; a deeper one is refused). Making a crate or folder at the top or inside a folder, renaming, deleting and "Move to folder" (a folder, or the top level) are each one undoable operation. The same name in two different folders is fine; in one folder it is refused, crates and folders together, compared as in 1.9. Deleting a folder deletes everything in it, after a confirmation that says how many crates, folders and different tracks it holds; the Library tracks are never touched, and one Undo brings back every crate, folder, entry, position and order exactly. A folder can't be moved into itself or its own subfolder; a move puts the crate or folder last in its new folder, and moving it where it is already records nothing. The tree is listed in the sidebar under the stages (folders open and close; `/crates?crate=ID` chooses the one shown, and an id that names nothing shows nothing chosen) and on the Crates screen, where the header shows the rekordbox path. "Add to crate" names a crate by its place ("Friday residency › Warmup"). The send already writes the tree as it is (`send::crate_tree`). Notes, summaries, adding non-Library tracks (which would add them to the Library; 1cB-23), fit sorting and smart crates stay in 1c and Phase 3.
- **Playlist changes made in rekordbox** (1cB-3, 2026-10-28): a track the DJ adds to or removes from a crate's playlist in rekordbox joins or leaves the crate at the next send (1.10, "Crate membership"). That isn't an operation, so it has no Undo of its own, and an Undo of the crate change it overtook is refused. A crate renamed or moved in the app has no record at its new path, so changes the DJ made to the old playlist aren't taken in.
- **Complexity:** M. **Reuse:** `send::crate_tree`, which already turns the folder tree into the nodes the writer sends.

### Phase 2: Getting tracks in

#### 2.1 Inbox (watched folders)
- **What:** watch Downloads plus any pool or promo folders. Where new music lands is asked in onboarding, never assumed (4.2). New audio appears in the **Inbox**: identified (if opted in), fingerprinted and quality-checked. The goal is Inbox zero, and the sidebar badge counts what's left.
- **Labels, each with its reason, and filter chips:**
  - **New to you**
  - **Better file** ("FLAC vs your 320 MP3"). Its action is **Upgrade** (2.6), which is always asked, never automatic.
  - **Other cut** ("Radio Edit of your Extended"), in amber, because cuts are nearly interchangeable.
  - **Rework**, labeled neutrally, since it's new music.
  - **On your wishlist** (2.5).
  - **Already have:** in a collapsed group with one **Clear** button. These become extra files.
- **Actions:** **Add to Library** (prominent; Inbox files become managed copies by default, since Downloads is a fragile location, 2.6), **Not now**, and **Hide** (plain text, hard to hit by accident). All have Undo, and hidden files are recoverable (1.11).
- **Batches:** grouped the way files arrived (store order, pool pack, zip), with "Add all". Pool packs show one row per song, with its versions as checkboxes.
- **Previews start about a third of the way in**, only in the Inbox.
- **Read-only:** files stay where they landed.
- **How:** the `notify` crate. Wait until a file is stable, and ignore `.crdownload`, `.part` and `.tmp`. Zips are read in place, or extracted into the app's own staging area.
- **Complexity:** M.

#### 2.2 Identification & tag cleanup
- **Fields:** artist, title, version, remixer, label, year, catalog number, art.
- **Sources:** AcoustID → MusicBrainz and Discogs, each opt-in, plus existing tags. Every suggestion names its source ("MusicBrainz via AcoustID", "from a sibling file", "from the filename") and appears as a diff before anything is applied.
- **Offline:** it still works from tags, the filename/version parser, and sibling files.
- **Complexity:** L. **Reuse:** `enrich.rs`, the integration clients, credentials handling.

#### 2.3 Wishlists
- **Inputs, most reliable first:** a pasted tracklist → CSV (e.g. Exportify) → the Spotify API with your own client ID (opt-in). SoundCloud and Apple are CSV or paste only.
- **Matching:** normalized fuzzy matching, the version parser and ISRC. Results are *owned*, *owned, other cut* (counts as owned), *you have a rework* (a hint, not owned) or *missing*, each with its reason.
- **B2B:** partner tracks from a session (3.6) go to a wishlist in one step.
- **Complexity:** M. **Reuse:** the `integrations/spotify.rs` harness.

#### 2.4 Missing list + store links
- One-click search links to Beatport, Bandcamp, Traxsource and Juno (URL templates only; the app makes no network calls), a "bought" toggle, and notes. No prices.
- **Complexity:** S.

#### 2.5 Auto tick-off
- **What:** when an Inbox file matches a wishlist item, the item is marked acquired and the track goes straight into the Library.
- **"Done for you":** these are listed at the top of the Inbox, saying which wishlist item matched and how. Undo returns the file to the Inbox.
- **Optional:** add it to a crate named after the wishlist.
- **Complexity:** S.

#### 2.6 Managed copies & upgrades
Moved out of the MVP. Needs gate tests T2 and T4 (§7) first.
- **What:** a Library track can become a **managed copy**: the best file's audio → rules gate → convert to the Library format (never upconvert) → complete tags and art gathered from all the track's files (1.7) → named by the template → written into the Library folder through the write guard.
- **When:** on request, for Inbox files (2.1), when the user makes a fragile-location track safe (1.3), or on an accepted **Upgrade** (1.7).
- **First use** asks for the Library folder and format (§1.1).
- **A copy of a rekordbox-known track** is a new Location, which rekordbox treats as a new track. rekordbox's data, including cues and grid, is sent with it (1.9 rule 3, case B). The old rekordbox entry stays, and the app lists it for manual removal. How safely cues carry over, especially after a re-encode, is T2.
- **Library copy tags:** complete, matching the XML exactly, in a fixed frame order, ID3v2.3, and including `TKEY` once rekordbox has reported the key (§5.1; T4 decides the details).
- **Upgrades:** the copy is regenerated at the same path. Cues, grid and alignment survive a same-settings re-encode, **but only after Reload Tag** in rekordbox, so the app lists the affected tracks and walks the user through it.
- **Durability:** a copy survives its original disappearing ("original file missing").
- **Identity:** Library copies are identified by audio hash.
- **Complexity:** M. **Reuse:** `plan.rs`, `execute.rs`, `vet.rs`, `policy.rs`, plus the Phase 2 ports (0.2).

#### 2.7 Read rekordbox's library directly (optional)
- **What:** an optional reader for rekordbox's own library database (`master.db`), so the app can read rekordbox's current values without the user exporting XML first. What it reads feeds the same place an XML read does, so matching, conflicts and the send work unchanged. Sends stay XML (1.9).
- **Optional, off by default** (§1.1, CLAUDE.md "Optional features"). Turning it on asks for the database key, which the user supplies. The app never ships, fetches, shows or hard-codes a key.
- **Read-only.** The app never writes to rekordbox's database. It reads a copy taken into its own data folder, so a running rekordbox is never disturbed.
- **One removable module.** It joins the core only where an XML read enters, so it can be switched off or taken out as a single feature. With it off, or when a read fails, the XML path works exactly as before.
- **Beyond the XML:** what else it reads is decided when the feature is broken down. Candidates: My Tags (3.1) and play history (3.6).
- **Not covered:** OneLibrary's `exportLibrary.db` on gig USBs isn't read.
- **Complexity:** M. **Reuse:** none; new.

### Phase 3: Set prep

#### 3.1 Custom tag vocabulary
- **What:** tag groups you define (vibe, role, vocal, situation), colored, applied from the keyboard and filterable.
- **Import first, don't start empty:** the vocabulary starts as a one-to-one copy of your existing rekordbox My Tags.
- **Into rekordbox:** reading works (1.2). The app hides the `/* … */` block when showing comments and never writes inside it. Writing My Tags is untested (T5). The fallback is comment text plus per-tag playlists under the app's folder.
- **Complexity:** M.

#### 3.2 Genre taxonomy with aliases
- **What:** a genre tree you control, with aliases mapping the mess to canonical nodes. Unmapped genres go to a review queue, and each mapping says which alias rule applied.
- **Seed:** broad and genre-neutral, with real branches across electronic, hip-hop, R&B, pop, rock, Latin, throwbacks and more. The `Parent (Sub)` convention (e.g. `Drum & Bass (Neuro)`) is supported as a style, not assumed as the tree's shape. Files with no genre are the first review queue.
- **Genre belongs to the track, not the song.** A dubstep VIP of a house tune keeps "dubstep".
- **Complexity:** M.

#### 3.3 Smart crates
- **What:** rule-based crates, exported as static playlists refreshed on each send. A rule AST compiles to SQL.
- **Rules read like a sentence:** "energy is at least 7 and tag includes peak", built from dropdowns, with a live count. A text version is available, and smart crates get their own sidebar icon.
- **Always include / Never include** lists (`crate_entry.kind`). Dragging a track onto a smart crate always-includes it; removing one never-includes it.
- **Library tracks only.**
- **Complexity:** M.

#### 3.4 Harmonic "what's next"
- **Signals:** Camelot compatibility, BPM (including half/double time), energy delta in the direction you want, tags and genre, your played transitions (3.6), and optionally audio-model similarity (3.8).
- **Explained:** each ranked track shows its top reasons ("8A → 8B, same BPM, you've played this after X twice"). The weights are adjustable and visible.
- **Tolerance:** covers both tight same-genre blending and bigger BPM or genre jumps, as a user setting, genre-neutral by default.
- The simple Phase 1 version is "Sort by fit" (1.14).
- **Complexity:** M.

#### 3.5 Playlists with an energy arc
- **What:** ordered playlists, made in the app or imported from rekordbox with their order kept.
- **Timeline view:** duration; the energy curve vs a target shape you draw; key and BPM flow with clashes flagged; "fill the gap" suggestions, each saying what gap it fills (key bridge, energy step, BPM). There's no transition preview.
- **Playlists double as crates:** every crate tool works on a playlist directly. "Save as crate" and "Start a playlist from this crate" convert between them.
- **They look different:** a crate sorts by any column; a playlist shows a `#` column and drag-to-reorder.
- **Complexity:** L.

#### 3.6 Play history import
- **What:** plays from every source become `play_event`s, grouped into **sessions**, which gives a transition graph. Play counts and last played already arrive in Phase 1 (1.2).
- **Sources:**
  - **m3u8 from rekordbox's History** (right-click → "Export a playlist to a file"): paths and order, one session at a time.
  - **Gig sticks** (`export.pdb`): "HISTORY 001…", in order but undated, and only the plays from that stick. Sessions are dated on import and can be corrected.
- **B2B:** a session can combine several sources. Without timestamps, interleaving needs the user's help (drag to order). Partner tracks you don't own are kept as plays and offered to a wishlist.
- **De-duplication:** the same gig can arrive twice (stick, then rekordbox after importing the stick). Match by track sequence (T6).
- **Complexity:** M–L.

#### 3.7 Local estimates
- **What:** fast BPM, key and energy (1–10) for tracks rekordbox hasn't analyzed, clearly marked as **estimates**. Until this lands, those tracks show no BPM or key until rekordbox analyzes them.
- **How:** pure Rust with `rustfft` (+ `ebur128`).
  - **BPM (ready):** spectral-flux onsets → comb autocorrelation over 60–200 BPM → fine search → folded into the user's rekordbox BPM range preference.
  - **Key (not shown yet):** use file key tags first, then rekordbox. Show local key only once it reaches ≥80% exact on the reference set.
  - **Energy:** loudness, onset density, spectral flux and BPM, calibrated by percentile within your own library, then against your own ratings. Mixed In Key `Energy N` tags are a source too. The stated basis reads like "loud, dense, fast for your library".
- **Reference set:** the tracks rekordbox analyzed in E1 become a **local** regression test. They're private, so CI uses a synthetic set with known BPMs.
- **Complexity:** L (key is the hard part).

#### 3.8 Local audio ML
- **What:** on-device models, downloaded once. The download is opt-in and goes through the network gate. The models are never part of the installer (§1.1, Optional features).
  - "Sounds like" similarity search, and a similarity signal for 3.4.
  - Genre and vibe **suggestions** (review only, never applied automatically).
  - A better energy estimate.
- **Always labeled:** ML output is presented as the audio model's opinion ("Audio model: sounds similar", "Audio model: Dubstep, 84%"). It is never the only reason for a suggestion, and it can be switched off in settings. Nothing else depends on it.
- **How:** ONNX Runtime via `ort` on the CPU. Embeddings are computed in the job queue and stored in `embedding`. Brute-force search is fine at 100k × 512 floats.
- **Models:**
  - **EfficientAT `mn10_as`** (MIT) for every track: an embedding plus AudioSet genre and mood tags in one cheap pass.
  - **LAION-CLAP music** (Apache-2.0/CC0), run lazily: "sounds like" plus text search.
  - Later: small per-user heads trained on the user's own genres and tags.
- **Constraints:** GPL-compatible weights; pinned model versions; credit for CC-BY models. The training-data licensing (AudioSet/LAION) goes to legal review.

## 5. rekordbox behavior and known traps

This section is the single home for these facts. Other sections link here.

### 5.1 rekordbox writes into audio files
- It writes tag edits made in rekordbox (MP3), and its detected key as `TKEY` into files made by our encoder. It did *not* do this for 22 key-less store MP3s; T4 finds the trigger.
- It writes the `/* My Tag */` comment (FLAC) when "Add My Tag to the comments" is on.
- It rewrites AIFFs at import.
- It sets a new modified time on every file it adds or analyzes.
- Setting cues doesn't touch files.
- **A DJ's edit made in rekordbox after an export is in the file but not in the export.** The send review warns when a file changed after the export it's built from, by its modified time on disk at prepare or as a scan recorded it, and a file tag is never taken as rekordbox's value (1.10, "Second channel"; 1cB-4).
- **So:** never assume a rekordbox-managed file is unchanged; identify files by `audio_hash`; on an mtime-only change, check a partial hash before re-fingerprinting. After a tag rewrite (new size and mtime), skip the re-fingerprint when the hash stage is current and the `audio_hash` is unchanged (1aC-10).
- **Reload Tag is a full overwrite from the file.** It even blanks a comment the file lacks, so Library copy tags must be complete.

### 5.2 XML import behavior (rekordbox 7)
These are observed behaviors, not documented ones, and any 7.x update can change them. **Re-run the rekordbox behavior check** (`spikes/rb-kit/CHECK.md`, about an hour; it includes the T1/T3 gate tests, built in 0D) after every rekordbox update, before trusting sends again.

- A first import raises no dialog about the tracks (with auto-analysis on, rekordbox shows its analysis-settings popup on each add). Awkward paths resolve: accents, `# % + & '`, CJK, emoji.
- On first import, XML values win over the file's own tags. This covers title, artist, album, genre, comments, rating, color, composer, remixer, label, mix, year and track #.
- On a first import with auto-analysis on, BPM and key from the XML are ignored. **On a Yes re-import they are loaded** (`AverageBpm`, `Tonality`), even over rekordbox's own analysis, while its grid stays: the BPM shown can then disagree with the grid. Omitting them keeps rekordbox's values (T3).
- **Re-importing an existing track asks per track, Yes or No** ("don't ask again" exists). **Yes is a full overwrite from the XML**: it undid a rekordbox-side title edit even though the XML hadn't changed that value.
- **A missing attribute can reset data** (an omitted Rating became 0), and **a default can erase it** (`PlayCount="0"` wiped real plays). An omitted Colour was kept. That's inconsistent, so never rely on omission.
- Cues and grids the XML doesn't mention are left alone. My Tags and playlists made in rekordbox survive.
- Same-name playlists are **replaced**, contents and order. Playlists missing from the XML are left behind. Tracks missing from the XML stay in the collection.
- TrackIDs are stable between exports but **reassigned on import**, so match by Location.
- Nested playlist folders and their order survive.
- **Unverified:** whether two playlists in one folder whose names differ only in letter case, Unicode form (composed or decomposed) or trailing whitespace count as the same name (and so replace each other). Until the behavior check covers it, the writer treats them as the same and refuses the send (1.9), and the merge of crate membership reads two such playlists of rekordbox's as one, their tracks together (1.10).
- **Unverified:** whether a re-sent track is matched to rekordbox's own when its `Location` is a network path, a macOS path, or any spelling other than `file://localhost/C:/…`. The behavior check only re-sent drive paths. Until it covers the others, the writer sends such a `Location` back exactly as rekordbox wrote it (1.9).
- **A playlist entry only resolves against the same XML's COLLECTION** (T1): an entry for a track not in it is dropped silently, whether keyed by TrackID (`KeyType="0"`) or Location (`KeyType="1"`). rekordbox exports every playlist as `KeyType="0"`.
- The re-import dialog is titled with the track name and offers Yes / No / Don't ask me again; replacing a same-name playlist asks OK / Cancel. Their exact wording is in the author's private 2026-09-28 check results.
- Last verified: rekordbox 7.2.19, 2026-09-28 (all checks except T1 behave as listed).

### 5.3 Parsing rekordbox exports
- `Location` has raw `# ( ) , + !` and lowercase `%xx`. Decode it by hand; a URL parser cuts at `#`. Besides drive paths (`file://localhost/C:/…`) it can be a network path (`file://localhost//server/share/…`) or a macOS path (`file://localhost/Users/…`).
- An export that isn't well-formed XML (cut off, a broken attribute, playlist folders nested absurdly deep) is refused as a whole, never read as a shorter collection: missing tracks would look deleted. Bad values inside a well-formed file only clear that field. A COLLECTION whose track count disagrees with its `Entries` is read but marked incomplete, and its missing tracks are never treated as removed (1aA-8, 2026-09-28).
- `Grouping` holds rekordbox's color name, not user data.
- Exported `Size` and `BitRate` can be stale, so always read them from the file.
- `TotalTime` is whole seconds, truncated, not rounded (255.634 s exports as 255).
- `Tonality` may follow the user's key-notation setting.
- Skip:
  - rows marked deleted (`rb_local_deleted`)
  - built-in demo tracks and samples (`Music\rekordbox\Sampler`, `Music\PioneerDJ\Demo Tracks`), matched as path components under `Music` for any user or drive, ignoring case
  - the "CUE Analysis Playlist"
  - streaming entries (`soundcloud:`, `spotify:`, any non-file scheme), kept in the snapshot and shown as "streaming, no file", never matched to a file
- rekordbox's default export folder is Documents.

### 5.4 Gig sticks
- rekordbox rewrites a stick's databases the moment it's plugged in. Read sticks with rekordbox closed, and never trust file dates for "when was this gig".
- `export.pdb` history is numbered but undated, and holds only plays from that stick.
- Old gig-USB copies inside music folders (`Contents\` in rekordbox's `Artist\Album\` layout) are a major source of exact duplicates. Grouping handles that.

### 5.5 Scanning
- Skip `._*` (macOS AppleDouble) and `.DS_Store`.
- The walk doesn't follow symlinks, junctions or mount points inside a music folder; a folder reached that way is indexed only if it's itself inside a music folder (1aA-4, 2026-09-29).
- Read tags leniently. Broken APE/ID3 blocks or a bad `TDRC` must not stop the audio being indexed.
- Detect the format from the bytes (a "`.wav`" can be an MP3).
- Flag truly broken files, such as an M4A with no `moov` atom from an interrupted download.
- OneDrive "online-only" placeholders trigger a download when read, so skip them unless the user opts in.

### 5.6 Engineering traps
- **Unknown tag frames** (Serato cues, custom frames) must survive every write. Port those tests first.
- **Our tag writer (lofty) isn't deterministic:** sort frames before writing so identical input gives identical bytes.
- **Migrations are never edited after they've been applied** (enforced in CI).
- **Read-only is enforced in code:** only the write guard (`write_guard`, 0E-7) hands out write access, scoped to the app data folder (the Library folder joins in Phase 2). It resolves links and `..` before allowing a path, refuses writes through hard-linked files, opens SQLite only on guarded paths, and blocks `ATTACH`, `VACUUM INTO` and temp-file redirection at runtime. A source scan fails CI on any write API outside the guard, and a runtime test checks nothing else changes. A file that must never be seen half-written (the rekordbox XML) goes through `write_then_rename`: a new file beside the destination, flushed, renamed over it, and deleted on any failure (1aE-7). What a write cut short by a crash leaves behind is cleared by `remove_leftover_parts`: exactly the names `write_then_rename` can give its new file, in that folder, plain files only. Both refuse a root itself as the destination, since the file beside it would be outside the root (1aF-1). The WebView2 profile Tauri keeps under `%LOCALAPPDATA%\com.tracklistpro.desktop\` is written by the runtime, not by app code.
- **The SQLite DB never lives in a synced folder;** it's in `%APPDATA%`. Its write-ahead log file (`tracklist-pro.db-wal`) is kept small (DOGFOOD C1-13, 2026-10-10): SQLite cuts it back to 32 MiB whenever the log starts again, and it's folded into the database and emptied when the database is opened, when the last job in the queue ends, and when the app closes (the process ends without closing its connections, so SQLite never tidies up by itself). A checkpoint that meets a read in progress gives up at once and the next of those points tries again; while one large transaction is still being written the log can be bigger than the limit. The repo itself lives off OneDrive too (`C:\dev\tracklist-pro`, CLAUDE.md "Parallel work"), so `.git`, `target/` and `node_modules` never sync.
- **Open files through `\\?\` paths on Windows.** A plain path drops trailing dots and spaces from names, so `Q.X.Z.\a.mp3` can silently open a sibling `Q.X.Z\a.mp3`, and names like `CON` can open devices on Windows 10. The path model resolves to `\\?\E:\…` or `\\?\UNC\…` (found in the 0C-9 review, 2026-09-28).
- **WebView2 can't play AIFF or ALAC,** so decode them in Rust for preview.
- **Coexisting with musicmanager:** different bundle ID, data folder, updater endpoint and credential-store prefix. Test both installed side by side.
- **MusicBrainz allows 1 request per second.** Every request passes through the network gate.
- **No API secrets in the binary.** Users bring their own Spotify and Discogs keys; AcoustID uses its application-key model.
- **Licensing:** LAME (LGPL), Symphonia (MPL-2.0), ONNX Runtime (MIT) and the model weights must all be GPL-3.0-compatible, checked by `cargo-deny` in CI.
