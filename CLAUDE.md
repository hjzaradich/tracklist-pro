# CLAUDE.md: tracklist-pro

A GPL-3.0 desktop app (Tauri 2 + Rust + React/TS) that builds a DJ's Library and keeps it in step with rekordbox 7 via XML. It's for any DJ who uses rekordbox on Windows, whatever they play. Windows is the only supported platform.

## Where to look
- **Before designing anything:** [ROADMAP.md](ROADMAP.md) §1 (principles, §1.1 decisions, §1.2 vocabulary) and §2 (data model).
- **Before touching rekordbox I/O, tag writing or scanning:** ROADMAP.md §5. It's the single home for rekordbox's behavior and the known traps.
- **What to work on:** [TASKS.md](TASKS.md). **Legal notes:** private (not in the repo); [NOTICE.md](NOTICE.md) is the public summary.
- Read the roadmap by section, not end to end.

## Must / never

**Files and disk**
- **Never** move, rename, retag or delete any file outside the Library folder. That includes files that linked Library tracks point to, and Inbox files. Only the write guard (`write_guard`) hands out write access, scoped to the app data folder (plus the Library folder from Phase 2); a source scan and a runtime test enforce it.
- **The MVP (Phase 1) never writes an audio file.** Every Library track is linked. Audio writes arrive with managed copies in Phase 2 (ROADMAP 2.6), and only into the Library folder.
- **Never** delete a Library track except through an explicit, confirmed, undoable in-app action.
- **Never** assume a file is unchanged because its mtime or size looks familiar. rekordbox rewrites tags and bumps mtimes. Identify audio by `audio_hash` and fingerprint, and detect formats from the bytes.
- **Never** match or relink on file size (§5.3).
- **Never** keep the SQLite DB in a synced folder. It lives in `%APPDATA%\com.tracklistpro.desktop\`.

**rekordbox**
- **Never** write to rekordbox's database, gig USBs or OneLibrary.
- **XML sends:** every attribute of every sent track, filled with rekordbox's current value from a fresh read. **Never omit or default** a field, except the analysis fields in ROADMAP 1.9 rule 3. Follow all eight rules in 1.9.
- **Always** read → merge conflicts → send in one step. **Never** silently overwrite a field edited on both sides; it becomes a conflict.
- **Always** parse `Location` by hand (raw `#`) and match tracks by Location, never by TrackID.
- **Never** read rekordbox's encrypted databases (`master.db`, OneLibrary), and never quote, link to or bundle their keys. Gig-USB `export.pdb` files aren't encrypted and may be read.

**Data model**
- A track is not a file. Duplicates merge; **versions never merge**, they're only linked (`version_link`), and nothing is inherited across a link.
- `analysis` is the source of truth for BPM, key and energy. `recording`'s values are derived from it and never edited directly.
- **Migrations are append-only.** Never edit an applied migration; add a new one.
- Every long operation goes through the job queue.

**Network and privacy**
- Every outbound request goes through the `net` module and checks the user's opt-in for that service. No other module makes HTTP calls. Model downloads and update checks count as services.
- **No telemetry, ever.** No API secrets in the binary; users bring their own keys.
- Respect MusicBrainz's limit of 1 request per second.

**Suggestions**
- **No black boxes.** Every suggestion reaching the UI carries a short, plain-language reason shown with it. If there's no reason, don't suggest.
- ML output is labeled as the audio model's opinion, is never the only reason, and must be switchable off. ML genre and mood suggestions are never applied automatically.

**Tests are the review**
- The owner can't line-read most Rust, so **every task ships with its tests**, and a task is done only when CI is green.
- Tests cover the behavior the task describes, including the must/never rules it touches (e.g. a write-guard or network-gate case).
- **Never** make CI depend on files in `spikes/results/`; most are private and git-ignored. Use generated or synthetic fixtures, and keep real-library checks as local-only tests.

**Code**
- Use the §1.2 vocabulary in UI and code; `recording`, `promote` and `job` (UI: Activity) are the code-only exceptions. One word per concept.
- All UI strings go through `i18next`; no raw strings in JSX. No hardcoded colors; use theme tokens.
- **User-facing copy is the owner's call.** Phrases and sentences shown in the app (empty states, help text, warnings, errors, confirmations, suggestion reasons and their templates, onboarding) are proposals. Put them in the locale file, list every new or changed phrase in your report under "Copy for the owner", and the owner approves or rewrites them before merge. Single-word labels and §1.2 vocabulary don't need approval. Draft in the owner's style: [docs/copy-style.md](docs/copy-style.md).
- TS bindings are generated by `tauri-specta`. Never hand-edit them. 64-bit integers cross IPC as TS `number` (the exporter casts them); anything that can exceed 2^53 (nanosecond timestamps, hashes) must cross as a string or be converted first (e.g. to milliseconds).
- Tag writes preserve unknown frames byte-for-byte, and frames are sorted so identical input gives identical bytes.
- Every dependency and every ML model license must be GPL-3.0-compatible (`cargo-deny` in CI).
- Stay separate from musicmanager: different bundle ID, data folder, updater endpoint and credential prefix. Ported modules are copies, not shared code.

## Parallel work
Several Claude instances may work on the same stage at once ([TASKS.md](TASKS.md)).
- **Lane count:** run all of a stage's lanes at once when they don't share files, about 5–6 at most. Bundle small tasks so each lane is a real chunk of work; every lane has a fixed cost (a session, a review, CI runs, rebases).
- **A foreman session coordinates.** It writes each lane's brief, reviews and merges PRs, and keeps TASKS.md current. **Send your reports and questions to the foreman** with `SendMessage` (to `TLP · Foreman`); if you can't reach it, give the report to the owner as one fenced `text` block, ready to copy-paste.
- **Name your session first thing:** `TLP <stage>-<lane> · <short lane name>` (e.g. `TLP 0E-3 · Write guard`), using the session-title tool on "self". Owner-guided sessions use `TLP 👤 · <what>`. The names are how the owner and the foreman tell sessions apart.
- **One lane per instance.** Work only on the tasks in your assigned lane, in order. Don't start tasks from other lanes or the next stage. Skip 👤 tasks.
- **Keep the repo, worktrees and build output off OneDrive.** The repo lives at `C:\dev\tracklist-pro`; lane worktrees go under `C:\dev\tracklist-pro-lanes\`. The private, git-ignored files (`spikes/results/`, `archive/`, `private/`) live in a private, backed-up folder outside the repo, reached from it through directory junctions. **Never run `git clean -x` (or delete ignored files) in the main checkout:** it would delete the private files through the junctions.
- **Own worktree and branch:** one git worktree per lane, on a branch named `stage/<stage>-lane-<n>` (e.g. `stage/0E-lane-2`). Keep the branch rebased on `main`.
- **Don't edit TASKS.md checkboxes.** When a task is done, say so in your final message; the checkboxes are updated on `main` at merge time.
- **Shared files that cause merge conflicts:**
  - **Migrations:** outside the Phase 0 schema lane, add a new migration with the next free number *at merge time*. If `main` already took your number, renumber yours before merging. Never renumber or edit a migration that's on `main`.
  - **Generated bindings:** don't hand-resolve conflicts in the generated `tauri-specta` file. Regenerate it after rebasing.
- **i18n types:** `src/i18n/resources.gen.ts` is generated. After adding or removing a `src/locales/en/*.json` file, run `npm run i18n:types` and commit the result; on a conflict, regenerate rather than hand-resolve.
  - **i18n:** add strings to your feature's own namespace file, not a shared one.
  - **Dependencies (`Cargo.toml`, `package.json`) and route/sidebar registries:** keep additions minimal and one per line, so they merge cleanly.
- **Stay in your lane's code.** If your task needs a change to code owned by another lane in the same stage, stop and report it instead of making the change.
- **Review before merge:** a separate reviewer instance reads each lane's diff against this file, the task and its tests, and reports problems before the lane is merged.
- **Green before merge:** the **CI result** check must pass on the PR's latest commit (e.g. `gh pr checks <N> --watch`). CI skips jobs a change can't affect on purpose (a docs-only PR builds nothing), and CI result fails if any job the change needed was skipped, failed or was cancelled. Branch protection on main requires the **CI result** check.
- **End of stage:** every lane is reviewed and merged into `main`, CI is green, and then the next stage starts.

## When the roadmap and the code disagree
Stop and ask rather than silently diverge. When a decision changes, update ROADMAP.md in its one home, and link to it rather than restating it.
